# Document Search Manager 開発手順

## 0. 着手前に必ず読むもの

1. **`document_search_manager/DESIGN_NOTES.md`** ← 最重要。
   調査で判明した事実、設計判断の理由、既知の罠がまとまっている。
   **ここを読まずに実装を始めない。** 特に以下は再発しやすい:
   - Graph の `listItem` は既定でタイトルを返さない（`fields` の明示要求が必要）
   - 拡張子の誤認識（社内は `12. Validation` `MRA2.0` のような命名が多い）
   - サイト判定は `/sites/` `/teams/` `/personal/` の3系統
   - **5-8**: `hidden` 属性は `display` を指定したクラスに負ける（**2回発生**）
   - **5-10**: Windowsでは同じポートに2つ目のサーバーが「成功」して起動する
   - **3-9**: Enoviaのセッションはセッションcookie。閉じる前に取らないと消える
2. `document_search_manager/CHANGELOG.md` の最新エントリ（直近の変更と未実施事項）
3. `document_search_manager/README.md`（利用者向けの仕様）

## 1. 絶対に守る制約

- **新規のEntra ID権限を申請しない。** 要求スコープは `Sites.Read.All` のみ。
  既存の `po_database_organizer` と同一のアプリ登録を流用する。
  この制約に反する実装案（SharePoint REST の直接呼び出し等）は**採用しない**。
- **推測で進めない。** 不明点は「未確認」と明記して質問する。
  対象システムの仕様が不明なときは、**実機のF12キャプチャを依頼する**のが最短。
- **変更を最小化する。** 依頼範囲外のファイル・ロジックを「ついでに直す」ことはしない。
  範囲外の問題を見つけたら、直さずに報告して判断を仰ぐ。
- **検証が通ったら、許可を待たずにコミット・Pushする**（2026-09-11にルール変更）。
  ただし**検証が通っていない状態・編集途中ではコミットしない**。
  Push先はそのセッションで指定された開発ブランチのみ。
  **プルリクエストの作成は、明示的な指示があったときだけ。**
- コミット後は、コミットハッシュと `git pull` コマンドをユーザーに伝える。

## 2. バージョン管理

- 本体ファイル名は `document_search_manager_YYYYMMDD_NN.py`。
  日付が変わったら NN は 01 にリセットする。
- **既存ファイルを上書きしない。** 必ず新しいバージョンファイルを作る
  （`cp` で最新版をコピーしてから編集する）。
- 旧版は `document_search_manager/old/` へ移動する。
  - ツール側も起動時に自動で退避するが、**リポジトリ側でも `git mv` で移動**すること。
    構成が一致していないと `git pull` で旧版が復活して重複する。
- `run_document_search_manager.bat` の呼び出し先を新バージョンに更新する。
  **バッチのコメントはASCIIのみ**（日本語UTF-8はCP932のcmdが誤解釈する）。

## 3. 実装の作法

- 設定・キャッシュ・出力のパスは `Path(__file__).resolve().parent` 基準。
  カレントディレクトリに依存させない。
- 画面のHTMLは Python の raw 文字列（`r"""..."""`）に埋め込む。
  JSの `\u{...}` エスケープが Python に解釈されないようにするため。
- 絵文字はJS側の文字列定数として定義する（f-string の外で扱う）。
- ダークテーマを維持する（bg `#1a1a2e` / accent `#e94560`）。
- 新しい設定項目を足したら `config.example.json` にも追加し、
  `_comment_*` キーで用途を日本語で説明する。
- 新しい系統（プロバイダ）を足すときは `SearchProvider` を継承し、
  `probe()` と `search()` だけを実装する。実行層・画面には手を入れない。
- **新しい一覧を作るときは、結果を `SearchResult` 型で組み立てる。**
  フォルダ探索はこれを守ったことで、絞り込み・並べ替え・選択・ZIP取得・
  Excel出力・要約が**無改修でそのまま動いた**。新規実装は探索処理と描画だけで済んだ。
- **CSSで `display` を指定したクラスに `hidden` 属性を付けるときは、
  必ず `[hidden] { display: none; }` も対で書く。** これを忘れて2回不具合を出した。
- **時間のかかる処理はジョブ化し、進捗を出す。** 起動→進捗取得の2段構え
  （`/api/explore` + `/api/explore_status`）が実績のある形。
  固まったように見せない。

## 3-2. 不明点の潰し方（S03で確立した型）

**推測で実装に入らない。** 代わりに、次の順で事実を確定させる。

1. **診断機能を先に1つ作る。** 本体の実装前に、必要な呼び出しだけを実際に試す
   小さな機能を作り、越智さんに会社PCで1回実行してもらう。
   実績: 「フォルダ探索診断」→ `/children` が現在の権限で通ることを確認してから本実装。
2. **F12のNetworkタブは万能ではない。** 別ホストへの通信は見つけにくい。
   **Consoleで `XMLHttpRequest` / `fetch` をフックする**方が確実
   （Enoviaの検索先が別ホストだったため、Networkタブで3回空振りした）。
3. **HARを依頼するときは「記録を開始してから操作する」と明示する。**
   逆順だと肝心のやり取りが記録されない（実際に起きた）。
   なお「サニタイズ保存」のHARには認証情報が含まれない。
4. **結果が「0件」「0個」のときは、それ自体が原因を指していることがある。**
   Enovia認証の解決は「セッションCookieが0件」という不自然さが唯一の手がかりだった。

### 診断機能・レポートを作るときの注意

- **判定を断定しすぎない。** S03では自作のレポートが実データに対して**2回**
  誤った結論を出した（「期限切れが原因」「ログインが完了していない」）。
  原因が複数あり得るときは、**候補を挙げて見分け方を示す。**
- **判定の根拠を実測値で表示する。** 「図面と判断しました」だけでは、
  誤判定かどうかをユーザーが判断できない。
- **秘密情報を出力しない。** Cookieの値・トークンは表示も保存もしない。
  名前・ドメイン・有効期限だけなら、そのままIT部門に共有できる。

## 4. 検証（必須）

```
cd document_search_manager
python -m py_compile document_search_manager_YYYYMMDD_NN.py
python tests/run_tests.py                              # ネットワーク不要
CHROMIUM_PATH=<chromeのパス> python tests/ui_check.py    # 画面の操作確認（任意）
```

- テストは `tests/_harness.py` が**最新バージョンを自動検出**する。
  バージョンを上げてもテスト側の修正は不要。
- **機能を追加・変更したら、必ず対応するテストを追加する。**
  `tests/test_NN_*.py` の形式で、目的別に分ける。
- **テストが落ちたら、まず切り分けて報告する。**
  - 「仕様変更に伴うテスト記述の陳腐化」なのか
  - 「機能の劣化（本物の不具合）」なのか
  前者なら期待値を更新し、**更新理由をコメントで残す**。黙って書き換えない。
- 画面まわりを変更したときは `ui_check.py` を実行し、
  **スクリーンショットを実際に目で見る。**
  S03では、単体テストを全部通過した状態で `hidden` が効かない不具合が残っており、
  **画像を見て初めて気付いた**。テストの合否だけで判断しない。
- **数値の制約を複数書くときは、掛け算して矛盾しないか確認する。**
  「300字以内。1文40字以内で2〜3文」は 40×3=120 で矛盾していた（指摘を受けた）。

## 5. CHANGELOG の書き方

`document_search_manager/CHANGELOG.md` の**先頭**に新しいエントリを追加する。
既存エントリは書き換えない。以下の見出しを使う。

```markdown
## VERSION YYYYMMDD_NN

（1行の要約）

### 追加 / ### 変更 / ### 修正
- 何をしたか。**なぜそうしたか（設計判断の理由）も書く。**
- 不具合修正は「原因」と「影響範囲」を明記する
  （表示だけの問題か、判定ロジックまで壊れていたか）。

### 変更しないこと（宣誓）
- 手を入れていない範囲を明記する（認証処理・検索ロジック等）。
- 旧バージョンファイルを削除していないことを明記する。

### 検証結果
- py_compile の結果
- 新規テストの項目数と内容
- 既存テストの再実行結果（累計項目数）
- ブラウザ操作テストで確認した内容

### 未実施（実機でのみ確認可能）
- 開発環境では検証できず、会社PCでの確認が必要な項目
```

## 6. 納品と報告

- 報告は**結論を3点、先に箇条書き**で述べ、その後に項目立てて説明する
  （各項目300字以内）。
- 必ず含める:
  - **適用手順**（`git pull` → 起動までのコマンド）
  - **実機で確認してほしいこと**（開発環境では検証できない項目）
  - 検証結果（テスト項目数）
- 不具合を自分で見つけた場合は**隠さず報告**する。
  「検証で実バグを検出しました」と明示し、原因と影響範囲を説明する。
- 画面を変更したときはスクリーンショットを `SendUserFile` で送る。

## 7. 各系統の現状と注意点（2026-09-11 時点）

### SharePoint（Phase 1・完了）

* Graph Search の `/search/query`（listItem方式）。
* **前方一致は原則使わない。** `P01*` が無関係な3687件を返した実測がある
  （`DESIGN_NOTES.md` 3-4）。使うときは最小文字数の条件付き。

### Nexus / Shareflex（Phase 2・完了）

* `path:` でDocumentsフォルダに限定する。標準Indexはリスト項目の `fields` から取る。
* 「Nexusで開く」は列フィルタ `@qmDocumentNo=` 方式。全文検索は使わない。

### Enovia / 3DEXPERIENCE（Phase 3・完了）

* 検索の実体は `POST federated.plm.nexperia.com/federated/search`。認証はcookieのみ。
* **タイトル限定検索は非対応と確定済み。** 推測で構文を足さない。
* **ログイン手順が特殊。** ログイン → **Enovia画面で1回検索** → ウィンドウを閉じる。
  検索を省くと `federated` 側のセッションが発行されず、必ず失敗する。
* **社外から会社PCで使う場合はVPNが必要。**
* **`enovia_document_type_only`（既定true）が、Document以外を捨てている。**
  クエリは191種類すべてを要求しており、**応答には既に含まれている**。
  Document以外を出したいだけなら、新しいAPI連携は不要。

### AI要約（完了）

* 共通モジュール `gemini_client.py` を使う。**M365 Copilotは採用しない**（新規権限が必要）。
* **見出しは形式を問わず `# ` に統一する**（docx=見出し / pptx=スライド /
  xlsx=シート / pdf=しおりまたはページ）。プロンプトを形式ごとに分岐させないため。
* プロンプトや出力形式を変えたら `SUMMARY_PROMPT_VERSION` を必ず上げる。
  上げないと古い形式の要約がキャッシュから出続ける。
* 図面が主体のPDFは要約しない（判定条件は `DESIGN_NOTES.md` 3-7）。

### フォルダ探索（完了）

* 幅優先。上限は深さ5階層 / 2000件。上限に当たったら理由をログに残す。
* 探索結果は `SearchResult` 型。既存機能は `scope=explore` で共用する。
* ツリー表示では並べ替えをしない（種別の絞り込みだけは可能）。

## 8. 実機確認の依頼の仕方

開発環境（Claude Code Web）からは社内システムに一切アクセスできない。
**「動くはず」で完了報告をしない。** 必ず次の形で依頼する。

* **手順を1行ずつのコマンドブロックで渡す。**
  複数行をまとめて貼ると、途中でエディタが開いたときに後続行が流れ込む（実際に発生）。
* `git pull` には `--no-edit` を付ける（マージコミットのエディタを開かせない）。
* **成功の目印を具体的に書く。** 「画面上部が `v20260911_02` になっていること」
  「ログに『うち検索に使えるもの 7 件』と出ること」など、見れば分かる形にする。
* **失敗したときに貼ってほしいもの**を先に指定する
  （画面のスクリーンショットだけでなく、コマンドプロンプトの出力も）。
* 実機確認が済んだら、**CHANGELOGの「未実施」を実測結果に置き換える。**
  推測のまま残さない。
