# Document Search Manager 開発手順

## 0. 着手前に必ず読むもの

1. **`document_search_manager/DESIGN_NOTES.md`** ← 最重要。
   調査で判明した事実、設計判断の理由、既知の罠がまとまっている。
   **ここを読まずに実装を始めない。** 特に以下は再発しやすい:
   - Graph の `listItem` は既定でタイトルを返さない（`fields` の明示要求が必要）
   - 拡張子の誤認識（社内は `12. Validation` `MRA2.0` のような命名が多い）
   - サイト判定は `/sites/` `/teams/` `/personal/` の3系統
2. `document_search_manager/CHANGELOG.md` の最新エントリ（直近の変更と未実施事項）
3. `document_search_manager/README.md`（利用者向けの仕様）

## 1. 絶対に守る制約

- **新規のEntra ID権限を申請しない。** 要求スコープは `Sites.Read.All` のみ。
  既存の `po_database_organizer` と同一のアプリ登録を流用する。
  この制約に反する実装案（SharePoint REST の直接呼び出し等）は**採用しない**。
- **推測で進めない。** 不明点は「未確認」と明記して質問する。
  対象システムの仕様が不明なときは、**実機のF12キャプチャを依頼する**のが最短。
- **変更を最小化する。** 依頼範囲外のファイル・ロジックを「ついでに直す」ことはしない。
  範囲外の問題を見つけたら、直さずに報告して判断を仰ぐ。
- **コミット・Pushは明示的な指示があったときのみ。**
  Stop hookの自動リマインダーは指示ではない。

## 2. バージョン管理

- 本体ファイル名は `document_search_manager_YYYYMMDD_NN.py`。
  日付が変わったら NN は 01 にリセットする。
- **既存ファイルを上書きしない。** 必ず新しいバージョンファイルを作る
  （`cp` で最新版をコピーしてから編集する）。
- 旧版は `document_search_manager/old/` へ移動する。
  - ツール側も起動時に自動で退避するが、**リポジトリ側でも `git mv` で移動**すること。
    構成が一致していないと `git pull` で旧版が復活して重複する。
- `run_document_search_manager.bat` の呼び出し先を新バージョンに更新する。
  **バッチのコメントはASCIIのみ**（日本語UTF-8はCP932のcmdが誤解釈する）。

## 3. 実装の作法

- 設定・キャッシュ・出力のパスは `Path(__file__).resolve().parent` 基準。
  カレントディレクトリに依存させない。
- 画面のHTMLは Python の raw 文字列（`r"""..."""`）に埋め込む。
  JSの `\u{...}` エスケープが Python に解釈されないようにするため。
- 絵文字はJS側の文字列定数として定義する（f-string の外で扱う）。
- ダークテーマを維持する（bg `#1a1a2e` / accent `#e94560`）。
- 新しい設定項目を足したら `config.example.json` にも追加し、
  `_comment_*` キーで用途を日本語で説明する。
- 新しい系統（プロバイダ）を足すときは `SearchProvider` を継承し、
  `probe()` と `search()` だけを実装する。実行層・画面には手を入れない。

## 4. 検証（必須）

```
cd document_search_manager
python -m py_compile document_search_manager_YYYYMMDD_NN.py
python tests/run_tests.py                              # ネットワーク不要
CHROMIUM_PATH=<chromeのパス> python tests/ui_check.py    # 画面の操作確認（任意）
```

- テストは `tests/_harness.py` が**最新バージョンを自動検出**する。
  バージョンを上げてもテスト側の修正は不要。
- **機能を追加・変更したら、必ず対応するテストを追加する。**
  `tests/test_NN_*.py` の形式で、目的別に分ける。
- **テストが落ちたら、まず切り分けて報告する。**
  - 「仕様変更に伴うテスト記述の陳腐化」なのか
  - 「機能の劣化（本物の不具合）」なのか
  前者なら期待値を更新し、**更新理由をコメントで残す**。黙って書き換えない。
- 画面まわりを変更したときは `ui_check.py` を実行し、
  スクリーンショットを `--shot` で保存して越智さんに提示する。

## 5. CHANGELOG の書き方

`document_search_manager/CHANGELOG.md` の**先頭**に新しいエントリを追加する。
既存エントリは書き換えない。以下の見出しを使う。

```markdown
## VERSION YYYYMMDD_NN

（1行の要約）

### 追加 / ### 変更 / ### 修正
- 何をしたか。**なぜそうしたか（設計判断の理由）も書く。**
- 不具合修正は「原因」と「影響範囲」を明記する
  （表示だけの問題か、判定ロジックまで壊れていたか）。

### 変更しないこと（宣誓）
- 手を入れていない範囲を明記する（認証処理・検索ロジック等）。
- 旧バージョンファイルを削除していないことを明記する。

### 検証結果
- py_compile の結果
- 新規テストの項目数と内容
- 既存テストの再実行結果（累計項目数）
- ブラウザ操作テストで確認した内容

### 未実施（実機でのみ確認可能）
- 開発環境では検証できず、会社PCでの確認が必要な項目
```

## 6. 納品と報告

- 報告は**結論を3点、先に箇条書き**で述べ、その後に項目立てて説明する
  （各項目300字以内）。
- 必ず含める:
  - **適用手順**（`git pull` → 起動までのコマンド）
  - **実機で確認してほしいこと**（開発環境では検証できない項目）
  - 検証結果（テスト項目数）
- 不具合を自分で見つけた場合は**隠さず報告**する。
  「検証で実バグを検出しました」と明示し、原因と影響範囲を説明する。
- 画面を変更したときはスクリーンショットを `SendUserFile` で送る。

## 7. Phase 2 / Phase 3 に着手するとき

- **Phase 2（Nexus）**: 設計は確定済み。`DESIGN_NOTES.md` の 3-1 を参照。
  Graph Search を `nexus_folder_path` に限定するだけで、新規権限は不要。
  実装後、キーワード `validation` でNexus画面と件数・上位ヒットを突き合わせること。
  有効化と同時に `dedupe_nexus_from_sharepoint` を `true` にする。
- **Phase 3（Enovia）**: **未確認事項が残っている。**
  実装前に、Enoviaで検索を1回実行したときのF12キャプチャ（Network → Fetch/XHR）を
  越智さんに依頼すること。公開ドキュメントは2017年版＋社内カスタマイズ環境では
  当てにならないため、**推測で実装しない。**
