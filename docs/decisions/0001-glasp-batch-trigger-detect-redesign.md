# ADR 0001: Glaspバッチ処理のトリガー/検出2フェーズ化

- ステータス: **実装済み（S03）。ただし後述のとおり1巡目の設計は実測により変更された**
- 対象ファイル: `youtube_summary_list.py`（`_batch_send_ctrl_x` / `_trigger_glasp_click` / `_wait_for_new_glasp_handle` / `_confirm_glasp_success`）

## S03での実装結果と設計変更（2026-08-09追記）

2フェーズ構成そのものは本ADRの設計どおり実装され、実機で成功率94%（74/79本）を達成した。ただし**1巡目（トリガーラウンド）の中身は、当初設計から変更された**。

- 当初設計: 1巡目で全動画にGlaspボタンを1回クリックし、その結果は捨てる
- 変更後: **1巡目ではクリックしない**。タブ切替・動画読込待ち・字幕確認・一時停止までを行い、Glaspのクリックだけ行わない（`prepare_only`）

変更の根拠は実測である。計測ログ（`glasp_measure.log`）を先に導入して1晩分のデータを取った結果、
- 1巡目のクリック64回に対し51枚（8割）が実際にGeminiタブを開いており、Googleへのリクエストを実質倍増させていた
- 一方で2巡目は52本中44本（84%）が1回目のクリックで成功しており、1巡目のクリックが助走として寄与している形跡がなかった

ことが判明した。**助走として効いていたのはクリックそのものではなく、タブを開いてから2巡目までに流れる時間**と判断し、時間の経過だけを残してクリックを外した。`config.json`の`glasp.round1_click`を`true`にすれば当初設計に戻せる。

なお本ADRが前提としていた「文字起こし生成に実時間がかかる」という仮説自体は、この変更後も維持されている（2巡目までの経過時間がその待ち時間にあたる）。

## 決定事項

`_batch_send_ctrl_x`のバッチ処理を、現在の「1本ずつ完結させてから次へ進む」方式から、

1. **トリガーラウンド**: バッチ内の全動画タブに対して、順番に「タブ切替→準備確認→Glaspボタンを1回クリック」だけを行い、Geminiタブの検出は待たずに即座に次の動画へ進む
2. **検出＆リトライラウンド**: トリガーラウンドが全動画分完了した後、改めて各動画を順番に確認し、Geminiタブが検出できていなければ再クリックする

という2フェーズ構成に変更する。

## 採用理由（根拠）

S02で以下の事実が判明した。

1. Glaspのきらきらボタンをクリックすると、YouTube側に文字起こし生成パネル（スピナー付き）が開く。これはクリックの**結果**であり、クリック前にDOM上で存在確認できる「事前条件」ではない（この点は当初「パネルの完了を待ってからクリックする」という別案を検討していたが、越智さんの実機観察により前提が誤りと判明し、棄却した）。
2. 失敗した動画タブでも、放置後に手動で1クリックすると高確率でGemini/ChatGPTが起動する。これは、文字起こし生成に一定の実時間（バックエンド処理）がかかっており、放置している間に自然と完了することを示唆する。
3. 現行コードは同一動画に対して`retry_delay`（2秒）間隔で即座に再クリックし、かつ検出失敗のたびに`driver.refresh()`でページを再読み込みしている。これは生成途中の状態をリセットしてしまい、「未完了の期間中をひたすらやり直し続ける」悪循環になっている可能性が高い。
4. リトライ回数を2→5に増やす対策（VERSION 20260801_02）は、直近の実行結果（3/26本成功）を見る限り、単独では大きな改善につながらなかった。

以上から、「同一動画への即時リトライ」ではなく、「バッチ内の他の動画を処理している間の実時間経過」を積極的に利用する設計に変更する方が、実際に観察された成功パターン（放置後に成功する）に合致すると判断した。

## 不採用案とその理由

- **クリック前に文字起こしパネルの完了をDOMで確認してから起動する案**: 当初提案したが、パネルはクリックの結果として初めて現れるため、事前チェックが原理的に不可能であることが越智さんの実機観察（「Glaspのボタンを押さないとこの画面が出てこない」）で判明し、棄却した。将来、Glasp/YouTube側の挙動が変わり「クリック前に判定可能な兆候」が見つかった場合は再検討の余地がある。
- **リトライ回数のさらなる増加のみで対応する案**: VERSION 20260801_02で2→5に増やしたが効果が限定的だったため、リトライ回数だけを積み増す方向は見送り、リトライの「間隔・タイミング」自体を見直す方向へ切り替えた。
- **`driver.refresh()`を単純に廃止する案**: 動画プレイヤー自体の読み込み失敗（文字起こし生成とは別の要因）に対するフォールバックとしては引き続き必要な可能性があるため、廃止ではなく「2フェーズ化により発生頻度が下がることを期待し、まずは温存する」方針とした。2フェーズ化後も効果が不十分であれば、リフレッシュのタイミング自体も再検討する。

## 実装上の留意点（S03への申し送り）

- バッチ内の全動画分の「クリック直前のwindow_handlesスナップショット」を同時に保持する必要がある
- キャンセル操作（`state.cancel_flag`）・スキップ操作（`state.skip_flag`）の扱いは、トリガーラウンド・検出ラウンドそれぞれで現行同様に効くようにする
- `browser_mode==3`（タブ連続運転）時のタブ再利用・後片付け処理（`_cleanup_batch_tabs`）との整合性を確認する
- `_send_ctrl_x_with_retry`内の「クリック処理」と「検出処理」を関数として分離し、トリガーラウンド/検出ラウンドの双方から呼び出せる形にする
