# ADR 0002: Googleの確認画面(reCAPTCHA)は「URLで検知し、中止せず待機する」

- ステータス: 実装済み・実機で動作確認済み（S03、2026-08-09）
- 対象ファイル: `youtube_summary_list.py`（`is_challenge_url` / `_confirm_glasp_success` / `_suspend_until_challenge_cleared`）、`check_suspend_lock.py`、`run_youtube_all_tasks.bat`

## 決定事項

1. **確認画面の判定はURLで行う。** URLのスキーム＋ホスト＋パス部分に `/sorry/` または `/recaptcha/` を含むかで判定する（`is_challenge_url()`）。ページ本文のキーワードでは判定しない。
2. **検知したら中止せず待機する。** それ以上Glaspを叩かず、溜まったタブを片付け、確認画面のタブを1枚だけ画面に残して人が手で解除するのを待つ。解除を検知したら、中断した動画から処理を続行する。
3. **待機中は定時チェーン全体を空振りさせる。** `glasp_suspended.lock` を書き、`run_youtube_all_tasks.bat` 冒頭の `check_suspend_lock.py` がそれを見て Step1〜3 を丸ごとスキップする。
4. **確認画面を突破する実装は行わない。** これはアカウント保護のための仕組みであり、破る方向の実装は本プロジェクトの対象外とする。取りうる方向は「検知して速やかに止める」と「そもそも検知されない程度まで自動化の圧を下げる」の2つに限る。

## 採用理由（根拠）

### なぜURL判定か

20260808の夜間実行で、20:07:24以降に29本が連続失敗した。ログ解析の結果、Geminiへの遷移が54回すべて

```
https://www.google.com/sorry/index?continue=https://gemini.google.com/...
```

に差し替えられていた（GoogleのBOT判定による確認画面）。Geminiタブが空だったのではなく、そもそもGeminiに到達していなかった。

前日に実装した検知機構は発火しなかった（`CHALLENGE_DETECTED` 0件）。原因は、検知を `_quick_success_check()` 内でページ本文のキーワード（`通常と異なるトラフィック`・`recaptcha`・`ロボットではありません` 等）で行っていたことにある。実機のページ文言が想定と異なり、代わりにエラー用キーワードに一致したため、**確認画面が「ただのエラー」として扱われ、静かにリトライが繰り返されていた**。

このとき本文をログに残していなかったため、事後に「実際に何と書かれていたか」を特定できなかった。**ページ文言は想定が外れうるうえ、外れたことを事後検証する手段もなかった**のに対し、URLは54回すべてログに残っており、文言に左右されない。したがってURLを一次判定とする。

補助として、判定が外れた場合にページ本文の先頭200文字をログへ残すようにした（次に未知のページが出た場合に一発で分かるようにするため）。

### なぜ中止ではなく待機か

当初は「検知したら実行全体を中止し、次の実行時刻に回す」方式を実装した。しかし越智さんから「夜間に発生した場合、朝までの実行機会がすべて失われる。手動で解除できるなら、そこから再開したい」という要望があり、待機方式へ変更した。

実機で「21:42:32 検知 → 待機 → 手動解除 → 21:43:33 自動再開」（61秒）まで確認済み。

### なぜチェーン全体を止める必要があるか

要約（Step3）だけを止めるのでは不十分である。`run_youtube_all_tasks.bat` の **Step1 はプレイリストからの動画削除**であり、要約が終わっていない状態でこれが先に走ると、**未要約の動画がプレイリストから消える**（`youtube_list_remove.py` は「先頭からN件削除」で、要約済みかどうかを見ていない）。したがって待機中はチェーン全体を空振りさせる必要がある。

## 不採用案とその理由

- **ページ本文のキーワードで判定する案**: 上記のとおり実機で素通りした実績があるため不採用。文言の追加で対応する案も検討したが、「次も想定が当たる保証がない」ため、根本的にURL判定へ切り替えた。
- **検知したら中止する案**: S03の途中まで実装していたが、夜間発生時に朝までの実行機会を失うため、越智さんの要望により待機方式へ変更した。ただし**待機の期限切れ時は従来どおり中止する**（翌朝7:00、ただし最長11時間）。
- **確認画面を自動で突破する案**: 検討していない。アカウント保護の仕組みを破る方向の実装は行わない方針を明示的に採用した。
- **待機中にGeminiへ定期的にアクセスして解除を確認する案**: 解除検知のために自動リクエストを繰り返すのは、確認画面を誘発した原因と同じ行為であるため避けた。代わりに**残しておいた確認画面タブのURLを読むだけ**とし、Googleへの追加リクエストを発生させない（解除するとGoogleが `continue=` 先へ遷移させるため、URLの変化だけで判定できる）。タブが閉じられた場合のみ、フォールバックとして1回だけGeminiを開き直す。

## 実装上の留意点

- **ロックファイルは必ず消えるようにすること**: 残ると夜間チェーンが永久に止まる。`_suspend_until_challenge_cleared()` は `finally` で削除し、`check_suspend_lock.py` 側も期限切れ・破損したロックを自動削除する（壊れたロックで止まり続けるより、通常実行に倒す方が害が小さいと判断）。
- **BATから `python` を裸で呼ばないこと**: `check_suspend_lock.py` を `python check_suspend_lock.py` と `call` なしで呼んだ結果、制御が戻らずチェーンが1秒で終了し、要約が2日間走らなかった。本プロジェクトの他のBATと同様、`python.exe` のフルパスで呼ぶこと。
- 待機に入る前に溜まったタブを掃除すること（朝まで大量のタブを開いたまま放置しない）。
- 待機直後の動画は、確認画面の検知で試行回数を1回消費するため失敗しうる。実機でも1本発生したが、その動画は後続の実行で成功したため許容範囲と判断した。
