## 1. 結論（要旨）

1. **ガバナンス設計は高く評価できる。** Premium禁止、証拠固定、fail-safe TestMode、Gate方式、DEV→TEST→PROD、変更禁止事項の明文化は、前セッションで露呈した「Azure ADアプリ登録＋管理者同意が個人では取得できない」問題への正しい回答である。この枠組みは維持すべき。

2. **一方で、Gate C（JMA XML本文取得）は「未確認」ではなく、ほぼ確実に不合格である。** 資料はこれを未解決ゲートとしているが、外部仕様を調査した結果、現行制約（Premium HTTPコネクタ禁止）の下では原理的に成立しない。6フローのうちEQ01・EQ02が実装不能であり、アーキテクチャ図の上流2段が機能しない。

3. **判定ロジック `earthquake_evaluator.py` には、誤発報と発報漏れを同時に生む構造的欠陥がある。** 実コードで再現・実証済み。資料自身のテスト項目T21・T25が、この欠陥を検出する項目でありながら未実装のため、「全自動テスト合格」という記載が誤った安心感を与えている。

4. **EQ04の実装仕様（直列ループ内での応答待ち）は、災害時に運用不能である。** 18名への送信が1人目の回答待ちで停止する。資料はこれを性能調整項目として扱っているが、要件を満たさない設計上の誤りである。

5. **推奨する方向修正は「トリガー境界での分割」である。** 価値の大半（安否確認〜集計〜上司通知）は標準コネクタのみで構築可能であり、IT部門への申請も不要。地震の自動検知だけを切り離し、第1段は手動トリガーで完成・運用開始すべき。

## 4. 重大な指摘

### 4.1 【最重要・技術】判定ロジックが誤発報と発報漏れを生む

`simulator/earthquake_evaluator.py` のシグネチャは次のとおり。

```python
def evaluate_sites(sites, areas, intensity_code) -> list[str]
```

`areas` は地域名の**フラットな文字列リスト**、`intensity_code` は**単一の震度**である。すなわち「全地域が同一の震度である」という前提でモデル化されている。

しかし現実のJMA震度速報は**地域ごとに異なる震度**を持つ。この不一致により、次の2つの障害が同時に発生する。

実コードによる再現結果（サイト定義＝大分県・大阪府・東京都、閾値＝震度5弱）：

| 入力 | 渡す震度 | 結果 | 本来の期待 | 障害 |
| --- | --- | --- | --- | --- |
| 大分=6強, 大阪=3 | 最大震度 `6+` | `['OITA', 'OSAKA']` | `['OITA']` | **大阪で誤発報**（ほとんど揺れていない拠点に安否確認が飛ぶ） |
| 大分=6強, 大阪=3 | 最小震度 `3` | `[]` | `['OITA']` | **大分で発報漏れ**（震度6強なのに安否確認されない） |

単一スカラーである以上、最大値を採ればどこかで誤発報し、最小値を採ればどこかで発報漏れする。**中間の選択肢は存在しない。**

これは資料自身のテスト項目 **T25「最大震度と対象サイト震度が異なる」** そのものであり、現アーキテクチャでは構造的に合格できない。

さらに、同じフラット照合により **T21「同じ市名が異なる都道府県に存在する」** も誤判定する。

| 入力 | サイト定義 | 結果 | 本来の期待 |
| --- | --- | --- | --- |
| 大阪府(5-), 東京都府中市(5-) | 大阪府＋府中市 | `['OSAKA_FUCHU']` | `[]`（大阪府に府中市は存在しない） |

都道府県と市区町村を同一の集合に対して独立に照合しているため、「大阪府が含まれる」かつ「府中市が含まれる」で成立してしまう。

**注目すべき点として、SharePointスキーマ側は正しい。** `EQ_Events` は `SiteIntensityCode` / `SiteIntensityValue`（サイト別震度）を持ち、`EventID` も `EQ-YYYYMMDD-HHMMSS-SITECODE` とサイト単位である。つまり**スキーマは正しく、判定コードだけが追随していない**内部矛盾である。修正方向は明快で、コードをスキーマに合わせればよい。

#### 修正版の提示

改訂版 `earthquake_evaluator_v2.py` を作成し、次の3点を修正した。

1. 入力を `AreaIntensity(prefecture, intensity_code, municipality)` の配列とし、地域ごとの震度を保持（引継ぎ資料 §12 Step 4 の `areaIntensities` 形式に一致させた）
2. 市区町村照合を都道府県スコープ内に限定
3. 戻り値を `SiteHit(site_code, intensity_code, intensity_value)` とし、サイト別震度を返す（`EQ_Events.SiteIntensityCode` に対応）

テストを4件→**17件**に拡充し、T21・T22・T25を含めて全件合格を確認した。

```

```

### 4.2 【最重要・実現可能性】Gate C は「未確認」ではなく不合格の見込み

資料は Gate C（JMA Atom → XML本文取得）を最重要未解決ゲートとしている。外部仕様を調査した結果、**現制約下では成立しない**と判断する。

根拠：

1. JMA防災情報XMLのPULL型提供では、Atomフィードは**電文本文へのURLを返すのみ**であり、震度の地域別内訳はリンク先のXML本文に格納されている。地域別震度を得るには、このURLを別途取得する必要がある。
2. Power AutomateのRSSコネクタはStandardだが、**フィードの標準フィールドを返すだけで、任意URLの本文を取得する機能を持たない。**
3. 任意URLの取得には**HTTPコネクタが必要であり、これはPremium**である。

資料 §4.1 は「Premium HTTPを追加しない」を変更禁止事項としている。したがって Gate C は制約と技術的必要性が正面衝突しており、**現構成のままでは自動地震連携を実装できない。** 資料自身のエラーコード SRC-002「XML本文取得不可 → Gate C失敗、開始禁止」が発動する状態である。

これは資料の欠陥ではなく、資料が正しく設置したゲートが**実際に不合格だった**というだけである。ただし、6フロー構成のうち5フローが Gate C 通過を前提としている点で、アーキテクチャ図が実現可能性を過大に見せている。

### 4.3 【重大・運用】EQ04の直列ループ内応答待ちは災害時に機能しない

`docs/04_FLOW_SPEC.md` および引継ぎ資料 §8.5 の仕様：

```
9. LOOP_Each_Member with concurrency initially set to 1
10. TM_Post_CheckIn_And_Wait using current non-deprecated Teams action
```

`Post adaptive card and wait for a response` は**ブロッキング動作**である。これを並列度1のループ内に置くと、**1人目が回答するまで2人目にカードが送信されない。**

災害時、1人目が負傷・圏外・就寝中であれば、後続17名にはカードが届かない。安否確認システムとして要件を満たさない。資料はこれを「初期テストの並列度」と位置づけているが、性能調整ではなく**設計上の誤り**である。

並列度を上げても、18本の実行分岐がそれぞれ応答待ちを保持する構成であり、タイムアウト・実行時間制限・再実行時の扱いが複雑になる。

**正しい構成は非同期分離である。**

- カード送信フロー：18名へ**投げ切り**（待たない）
- 回答受信フロー：カード応答を**トリガー**として起動し、SharePointへUpsert＋上司通知

この分離により、送信は即時完了し、回答は各自のタイミングで独立に処理される。

### 4.4 【重大】Gate B のTeamsアクションは廃止済みの可能性が高い

調査の結果、1:1チャット向けの `Post adaptive card and wait for a response` は**Deprecated**とされている。資料 §8.1 の停止条件「TeamsアクションがDeprecatedしか選べない」に該当する可能性が高い。

代替は「カードを投稿する」アクションと「カードに応答があったとき」トリガーを分離する非同期パターンであり、**§4.3の修正方向と一致する。** すなわち、Gate B の問題と EQ04 の設計欠陥は、同一の修正（非同期化）で同時に解消する。

なお、Teamsコネクタ自体はStandardである一方、一部の解説はこのアクションにPremium相当のライセンスが必要と述べており、記述が一致していない。**実テナントのアクション選択画面でPremiumバッジの有無を確認すること**（Gate A/Bの実測項目）。

### 4.5 【重大・セキュリティ】秘密情報スキャンが機能していない

`scripts/validate_package.py` に実装上の不具合がある。

```python
SECRET_PATTERNS = [
    r"@[A-Za-z0-9.-]+\.(com|net|jp|...)\b",              # [0] メールアドレス
    r"[0-9a-fA-F]{8}-[0-9a-fA-F]{4}-...",                # [1] GUID
]
...
for pattern in SECRET_PATTERNS:
    for match in re.findall(pattern, text, re.IGNORECASE):
        pass                                    # ← 何もしていない（デッドコード）
for m in re.finditer(SECRET_PATTERNS[0], text, re.IGNORECASE):   # ← [0]のみ検査
```

`SECRET_PATTERNS[1]`（GUID）は**定義されているが一度も評価されない。** その結果、資料 §4.4・§16 が明確に禁止している **Tenant ID・Team ID・Channel ID（いずれもGUID形式）がスキャンをすり抜ける。**

実証：`docs/02_ARCHITECTURE.md` に `TenantId: 3f2504e0-4f89-11d3-9a0c-0305e82c3301` および Channel ID を追記したうえで検証を実行した結果、

```
PASS: no obvious personal email address
PACKAGE VALIDATION: PASS
```

エラーコード SEC-001「秘密情報検出 → コミット禁止」が発動しない。**最も守るべき識別子を守れていない状態である。**

修正は2行程度（デッドループを削除し、全パターンを走査する）で済む。

### 4.6 【中】テストが誤った安心感を与えている

- テストマトリクスは30項目を定義しているが、実装されている自動テストは**4件のみ**。
- 未実装項目のうち **T21・T25 が、§4.1で示した構造的欠陥を検出する項目**である。最も重要な2項目が未実装のまま「PASS」と表示される。
- Definition of Done は「全自動テストが合格している」を条件としているが、この文言では4件合格でも満たされてしまう。**カバレッジ条件（マトリクス項目との対応）を明記すべき。**
- マトリクス自体にも重複がある：**T17とT26**（1名のTeams送信失敗）、**T07とT24**（取消電文）、**T15とT28**（TestMode欠損）。実質27項目であり、見かけの網羅性が水増しされている。

### 4.7 【中】テストデータが実要件と乖離している

`testdata/sites.json` のサイトは `OSAKA` / `KUMAMOTO` だが、実際の要件は**大分県・大阪府・東京都**である。

さらに `testdata/events.json` の `evt-005` は、大阪府と熊本県（約500km離れている）に**同一震度 `5+`** を与えている。これは §4.1 の誤ったモデルをテストデータとして固定化したものであり、修正時にはテストデータも作り直す必要がある。

## 5. 見落とされている論点

### 5.1 既存の安否確認サービスの有無を確認していない

多くの企業は既に商用の安否確認サービス（トヨクモ、セコム等）を導入している、あるいはBCP規程で連絡手段を定めている。**これを確認せずに並行システムを構築すると、**

- 災害時にどちらが正式な連絡経路か不明になる
- 「非公式のシステムに依存していた」ことが事後に問題化する

**着手前に、総務・人事・BCP所管部門へ「現行の安否確認手段」を確認すべき。** これは技術判断以前の前提確認であり、最も優先度が高い。

### 5.2 災害時に依存経路そのものが失われる可能性

本システムはTeams・SharePoint・社内ネットワークに全面依存している。停電・回線断・M365障害時には機能しない。SMS・電話は §3.2 でスコープ外とされており、**フォールバックが存在しない。**

これは今すぐ解決すべき課題ではないが、**「この仕組みは唯一の安否確認手段にはならない」という限界を、導入時に関係者へ明示的に伝える必要がある。** 資料のリスク記載に加えるべき項目。

### 5.3 個人アカウント依存（Gate Eの実質）

フローの所有者・接続認証が個人アカウントに紐づく場合、異動・退職・パスワード変更で停止する。資料は Gate E で共同所有を挙げており認識は正しいが、**「安否確認という業務の重要度に対して、個人所有のフローで良いのか」という組織的な問いには踏み込んでいない。** §5.1と併せて所管部門と合意すべき。

## 6. 方向修正の提案

### 6.1 基本方針：トリガー境界で分割する

現在の構成は「地震検知」と「安否確認」が1本の鎖でつながっており、**最も難しく制約に抵触する部分（地震検知）が、最も価値のある部分（安否確認）を人質に取っている。**

- **難しい部分**：JMA XML本文の取得（Premium必須＝IT申請が必要）
- **価値のある部分**：18名への安否確認〜4択回答〜集計〜上司通知（**標準コネクタのみで構築可能・IT申請不要**）

業務価値の大半は後者にある。したがって**後者を先に完成させ、運用を開始する。**

### 6.2 推奨ロードマップ

| フェーズ | 内容 | Gate依存 | IT申請 |
| --- | --- | --- | --- |
| **P0** | 既存の安否確認手段の有無を所管部門へ確認（§5.1） | なし | 不要 |
| **P1** | 手動トリガーの安否確認エンジンを完成・運用開始<br>（EQ06＋EQ03＋EQ04非同期版＋EQ05） | Gate A/B/D/E | 不要 |
| **P2** | 自動地震検知の方式決定（§6.4の3案から選択） | Gate C | 案により要 |
| **P3** | 訓練・多言語・他災害への拡張 | — | — |

**P1完了時点で、業務としては成立する。** 管理者がTeamsからボタンを押せば18名に安否確認が飛び、回答が集計され、被災者は上司へ即通知される。地震だけでなく台風・火災・訓練にも使える汎用性が得られる。

### 6.3 P1のアーキテクチャ修正（非同期化）

```
[手動トリガー / 将来は自動トリガー]
        │
        ▼
EQ02_Evaluator（サイト別震度で判定 ← v2ロジック）
        │
        ▼

        │
        ▼

        │
        ▼
    （各自が任意のタイミングで回答）
        │
        ▼
EQ04b_On_Response  ── カード応答トリガーで起動
        │            ├→ SharePoint EQ_Responses へUpsert
        │            └→ 被災・出社不可なら上司へ即通知
        ▼

```

§4.3・§4.4 の両方がこの1つの変更で解消する。**Gate B の確認項目も「wait for a response が使えるか」ではなく「カード投稿アクション＋応答トリガーが使えるか」に差し替えるべき。**

### 6.4 P2：自動検知の3案

| 案 | 内容 | 長所 | 短所 | 評価 |
| --- | --- | --- | --- | --- |
| **A** | **手動トリガーのまま運用** | IT申請ゼロ、即運用可、誤発報リスク最小 | 人が起動する必要がある（揺れを感じた管理者が押す） | **推奨。** RSSのポーリング遅延（数分）を考えれば、人的起動との時間差は実用上小さい |
| **B** | HTTPコネクタのPremiumライセンスをIT申請 | 完全自動化、正攻法 | 有料（1ユーザーまたは1フロー単位）、申請が必要 | **次善。** 「Azure ADアプリ登録＋テナント全体のMail.Send＋管理者同意」より**申請の重さが桁違いに小さい。** セキュリティレビューの観点でも通りやすい |
| **C** | ローカルの地震監視スクリプトからフローを起動 | 既存資産を流用できる | **起動経路の認証が未解決。** HTTPリクエストトリガーもPremium。実現方式が確立していない | **要検証。** 現時点で成立を主張できないため、P1完了後に別途調査 |

**重要な補足：** 前セッションで構築したPython版は、**社内ネットワークからp2pquake APIへの疎通が実機で確認できている**（`/internal/check` がエラーなく応答した）。したがって「社内から地震APIに到達できるか」という問いは既に解決済みであり、残る課題は「到達できたことをPower Automateへ渡す経路」だけである。案Cはここに賭ける案だが、経路の実現方式が未確定である。

### 6.5 EEW（緊急地震速報）について明示的な合意が必要

当初のご依頼は「緊急地震速報で震度5以上が出たら」であった。本パッケージは §1.2・§3.2 でEEWをスコープ外とし、**発生後の震度速報**を使う設計にしている。

**この変更は技術的に正しい。** EEWは揺れの数秒〜数十秒前に届くものであり、Power Automateのポーリング周期（分単位）では原理的に間に合わない。また安否確認は「揺れた後」に行う業務であり、EEWを待つ必要がない。

ただし**要件の実質的な変更であるため、依頼元として明示的に承諾すべき。** 「このシステムは地震の予知・警報ではなく、地震発生後の安否確認である」ことを、導入時の説明にも明記する。

## 8. 次に取るべきアクション

## 9. 総評

**この引継ぎ資料の枠組み自体は採用すべきである。** 前セッションで独自のPython＋Graph API構成が管理者同意の壁に当たった経験を踏まえ、「会社の環境に収まる範囲で作る」という方向転換は正しい。証拠固定・Gate方式・fail-safeの徹底は、この種の社内ツールでは稀なほど堅実である。

一方で、資料は**自らが設置したゲートの答えを出す前に、6フロー分の詳細設計まで進んでいる。** Gate Cが不合格であれば上流2フローは書き直しになり、Gate Bの結果次第でEQ04も構造から変わる。**設計の精緻さが、実現可能性の不確かさを覆い隠している**状態である。

加えて、オフライン検証済みとされた判定ロジックに、誤発報を生む構造的欠陥が残っていた。「仮想検証済み」の範囲を明示する姿勢は良いが、**検証項目そのものが要件（T21・T25）を満たしていなかった**点は、プロセスの穴として記録すべきである。

**推奨：Gate A・B・Dの実測を先に行い、手動トリガー版（P1）を完成させて運用に乗せる。自動検知は独立した判断として後続させる。** 6フロー同時着手は、最も不確実な部分に全体を人質に取られる構成であり、避けるべきである。
