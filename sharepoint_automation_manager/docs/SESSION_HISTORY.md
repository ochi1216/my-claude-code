## ADR-001: Excelデータ取得方式をGraph API直結に決定
- 日付：2026-09-17
- 状況：SharePoint上のExcelシートを定期的に読み取る必要がある
- 決定：Excelアプリを開かず、Microsoft Graph APIのworkbook/usedRange
  （またはrange）APIで直接セル値を取得する
- 却下した代替案：Excel COM自動化（GUI操作依存、会社PCでの安定性に懸念）、
  Power Automateの表内操作（GUI設定への依存度が高い）
- 理由：GUI操作を完全排除でき、既存のGraph API知見（SharePoint Portal,
  OneNote Report Generator）を流用可能

## ADR-002: 実行基盤をGitHub Actionsのスケジュールワークフローに決定
- 日付：2026-09-17
- 状況：定期実行の仕組みが必要。GUI操作を避け、即座に修正できる自由度が
  求められている
- 決定：GitHub Actionsのcronトリガーを軸とする
- 却下した代替案：Windows Task Scheduler（GUI設定依存、PC起動状態に依存）、
  Power Automate（ビジネスユーザー向けでGUI操作中心）、Azure Functions/
  Automation（Phase2で再比較予定、初期構築コストがやや高い）
- 理由：既存のGit運用実績（ochi1216/my-claude-code）と親和性が高く、
  yml編集のみでスケジュール変更が完結する

## ADR-008: 認証方式は既存ツールのMSAL Device Code Flow（委任権限）を流用する方針に決定
- 日付：2026-09-17
- 状況：Claudeの初期分析では「GitHub Actionsの無人実行にはClient Credentials
  Flow（Application権限）への切替が必要」と提案したが、越智さんより「既存ツール
  （r19_site_organizer／onenote_report_generator）と同じ認証方式をそのまま使え
  ないか。他ツールでも同様の流用をしている」との指摘があった
- 検討：Device Code Flowは初回サインインのみ対話操作が必要だが、その後はMSALの
  トークンキャッシュ（リフレッシュトークン含む）をGitHub Actions Secretsとして
  保管し、実行ごとにsilent refresh→更新後のキャッシュを書き戻すことで、無人実行
  が技術的に可能であることを確認した
- 決定：既存ツールと同じMSAL Device Code Flow・委任(Delegated)権限のパターンを
  流用する。Application権限への切替は行わない。初回サインインのみ越智さんご本人
  が実施し、以降はキャッシュの自動更新・書き戻しで運用する
- 理由：①既存の認証実装・App登録スコープをそのまま再利用でき開発量が減る、
  ②Application権限化に伴うテナント全体アクセスリスクを回避できる、③Phase0で
  IT/セキュリティに説明するスコープが既存承認済みパターンと同一のため、承認取得
  が容易になる
- 残存リスク：GitHub Actions Secretsに保管する内容が「単なるAPIキー」ではなく
  「有効なリフレッシュトークンを含むMSALキャッシュ」になるため、漏洩時の影響が
  より大きい。Phase0でこの点をIT/セキュリティに明示し、シークレットへのアクセス
  権限を必要最小限に絞ることを確認する（NEXT_TASK.mdのPhase0受け入れ基準③に反映）
- 状態：反映済み（前回提示したApplication権限化の提案は撤回）

## ADR-009: GitHub Actionsのcron実行タイミングは「17:00〜17:30」の許容幅を持たせる方針で承認
- 日付：2026-09-17
- 状況：GitHub Actionsのスケジュールワークフローは公式にも「ベストエフォート」
  であり、数十分規模の遅延・稀な欠落が報告されていることが判明した
- 決定：「17:00キッカリ」ではなく「17:00〜17:30の間に届けば正常」と定義する
- 理由：cronの構造的な遅延リスクを前提に、過検知（誤ってアラートを出す）を防ぐため
- 状態：越智さん承認済み

## ADR-010: KPIは3指標（効率化・信頼性・応答性）を併用する方針に決定
- 日付：2026-09-17
- 状況：Claudeが提示したKPI候補3案（手動時間削減／取得成功率／異常検知〜通知の
  応答時間）について、越智さんより「どれも達成したい」との回答があった
- 決定：3案は排他的選択肢ではなく、それぞれ異なる観点を測る指標として3つとも
  採用する
  - KPI-1（効率化）：手動確認時間の削減量。目標：年間約8.7時間
    （5分×週2回×52週）の手動確認をゼロ化
  - KPI-2（信頼性）：取得成功率。目標：月間実行8回中8回成功（100%）
  - KPI-3（応答性）：異常発生から通知までの平均時間。目標：30分以内
- 理由：NEXT_TASK.mdの受け入れ基準は「1つ以上の定量指標」だが、3指標を組み合わ
  せることでPM/上位マネジメントへの説明力が上がる
- 状態：越智さん承認済み
