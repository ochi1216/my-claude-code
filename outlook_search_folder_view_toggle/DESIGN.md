# Outlook 検索フォルダー 表示モード一括制御ツール — 設計レビューと改訂案

元となる構想（「検索条件は不変、表示モードだけを全体制御」）は方向性として妥当。
ただし、Outlook VBA のオブジェクトモデル特有の癖により、そのまま実装すると
以下の3点で事故りやすい。実装に入る前に潰しておくべき。

1. ビューの「共有スコープ」を確認せずにフィルターを書き換えると、無関係な
   フォルダー（受信トレイ等）まで巻き込む恐れがある
2. `View.Filter` を変更しただけで画面に反映されるか／`Save` が要るかは
   バージョン依存で未確定。ここを決め打ちすると「復元」の設計が変わる
3. VBA単体ではクイックアクセスツールバーへの自動登録ができない

以下、原案の何が良くて、どこを直すべきかを順に示す。

## 良い点（そのまま採用）

- 検索フォルダーの識別を **Store ID + Entry ID** で行う方針（名前だけに頼らない）
- 検索フォルダー本来の検索条件とビューフィルターを明確に分離する設計思想
- 対象外リスト（受信トレイ・送信済み・標準「未読メール」検索フォルダー）を
  初期状態で除外する誤作動防止策
- マクロ署名必須、`マクロをすべて有効化`を使わないセキュリティ方針
- 2フォルダーだけでのパイロット → 段階展開という検証の進め方

## 直すべき点

### 1. ビューの共有スコープを最初に診断する（最重要・追加が必要な工程）

Outlook のビューには `View.SaveOption` があり、値は
`olViewSaveOptionThisFolderOnlyMe` / `olViewSaveOptionThisFolderEveryone` /
`olViewSaveOptionAllFoldersOfType` のいずれかを取る。もし対象の検索フォルダーの
ビューが「この種類のすべてのフォルダーで共通」になっていた場合、
`View.Filter` を書き換えて `Save` した瞬間、**受信トレイなど無関係な
フォルダーの表示まで一緒に変わる**。これは原案の「非対象：メール本文、既読状態、
移動・削除」の対象外リストに「他フォルダーへの波及」が入っていないため、
見落とされている事故要因。

→ **フェーズ2（対象登録機能）の最初の処理として、各検索フォルダーのビューを
無条件に `SaveAs` で複製し、`olViewSaveOptionThisFolderOnlyMe`（このフォルダー、
自分のみ）の専用ビューに固定してから運用を始める。** これにより、どのフォルダーに
何をしても他フォルダーに波及しない状態を先に保証できる。

### 2. `View.Filter` は「変更→即描画」か「`Save`しないと反映されない」かを
   パイロットの最初の一歩で確定させる

原案は「バージョンにより上部の『未読』タブの強調表示まで完全一致しない
可能性は、パイロットで確認します」という書き方で、見た目の細部の検証に
留まっている。しかし本当に確認すべきはもっと手前で、**`Save`せずに
プロパティを変えるだけで画面に反映されるかどうか**という、設計の根幹に
関わる分岐点。ここでどちらの挙動かによって、後続の設計が変わる。

- **`Save`なしで反映される場合**：フィルターは「揮発性の重ね掛け」にできる。
  フォルダー切替時に毎回適用し直すだけでよく、「元のビューを保存して戻す」
  復元処理はほぼ不要になる（何も保存していないので、放っておけば元の状態のまま）。
  設計がシンプルになり、事故のリスクも下がる。
- **`Save`しないと反映されない場合**：フィルター変更はディスクの
  ビュー定義に永続化される。この場合は原案フェーズ5の「元のビュー・
  フィルターの保存」と「緊急復元マクロ」が必須になる。

→ どちらになるかで実装の複雑さも復元機能の要否も変わるため、
**検証計画の一番最初にこの分岐確認を追加**し、結果に応じて実装方針を
確定する（1.のビュー専用化をやっておけば、どちらの結果でも他フォルダーへの
実害はない）。

### 3. `Explorer.FolderSwitch` は Application 直下のイベントではない

原案フェーズ4は「Explorer.FolderSwitch」で発火すると書いているが、
Outlook の `Application` オブジェクトには `FolderSwitch` イベントは無く、
`FolderSwitch` は個々の `Explorer` オブジェクトのイベント。したがって：

- `ThisOutlookSession` の `Application_Startup` で、起動時点の
  `Application.ActiveExplorer` に対して `WithEvents` の監視オブジェクト
  （原案の `clsExplorerWatcher`）を1つ生成してアタッチする
- 2枚目以降のOutlookウィンドウは `Application_NewExplorer` イベントで
  捕捉し、同様に `clsExplorerWatcher` をアタッチする
- 各 `clsExplorerWatcher` が自分が監視する `Explorer` の `FolderSwitch` を
  受けて、対象登録済みフォルダーかどうかを判定し、モードを適用する

原案のモジュール構成（`clsExplorerWatcher` を用意している）は結果的に
正しい設計だが、フェーズ4の説明文だけを読むと「Application直下で拾える」
ように誤読されるので、実装メモとして明記しておく。

**見落としがちな抜け**：`Application_NewExplorer` は「起動後に新しく開いた
ウィンドウ」にしか発火しない。Outlook起動直後に最初から開いているウィンドウ
（`ActiveExplorer`）には発火しないため、`Application_Startup` 側で
明示的に初期アタッチ＋現在のフォルダーへのモード再適用を行う処理を
フェーズ4に追加する。原案のままだと「Outlookを開いた直後、最初に表示されている
フォルダーには前回のモードが自動で乗らない」状態になりうる。

### 4. クイックアクセスツールバー（QAT）への登録は自動化できない

Outlook VBA にはQATへボタンを追加するAPIが無い（COMアドイン＋リボンXML
なら可能だが、署名済みVBAプロジェクト単体では不可）。
「操作」節にある `未読モード：管理対象すべて` 等はマクロとしては用意できるが、
QATへ乗せる作業は**ユーザーが初回に手動で「その他のコマンド」→「マクロ」から
1回ピン留めする**という前提を明記する必要がある。原案には「配置」とだけ
書かれており、自動化できると誤解されるおそれがある。

### 5. Entry ID が無効になったときの扱い

登録済み検索フォルダーが後から削除・作り直しされると Entry ID が変わる。
`modSearchFolderRegistry` に、起動時（または `状態確認：管理対象一覧` 実行時）に
`Session.GetFolderFromID` が失敗した登録を検出し、「無効」として一覧に警告表示する
処理を追加する。フォルダー名の変更自体はEntry ID追跡なので問題にならないが、
削除には備えておく。

### 6. 複数データファイル（ストア）対応の明記

Exchangeメールボックスの他に共有メールボックスやPSTを開いている環境では、
検索フォルダーはストアごとに存在しうる。フェーズ1は `Session.Stores` を
ループしてストアごとに `Store.GetSearchFolders` を呼ぶ前提で書く
（越智さんの環境が単一ストアなら影響は無いが、想定外のストアで
検索フォルダーが見つからず「登録できない」という問い合わせを防げる）。

### 7. イベント頻度に対する軽量化の具体化

原案の「軽量化」方針（開いた1フォルダーだけ処理）は正しいが、
`FolderSwitch` はフォルダーツリーの矢印キー移動などでも連続発火しうる。
`modSearchViewController` に登録済み Entry ID を `Scripting.Dictionary` で
保持し、`FolderSwitch` ハンドラの先頭で対象外なら即 `Exit Sub` する
判定をO(1)にする、という実装レベルの指針を加えておく。

## 改訂版フェーズ構成

| フェーズ | 内容 | 変更点 |
|---|---|---|
| 0（新設） | ビュー共有スコープの事前診断＋専用ビュー化 | 各対象フォルダーのビューを `SaveAs` で複製し `ThisFolderOnlyMe` に固定 |
| 1 | 検索フォルダー台帳の取得 | `Session.Stores` をループして全ストアを走査するよう明記 |
| 2 | 対象登録機能 | フェーズ0の専用ビュー化とセットで実施 |
| 3 | グローバルモード機能 | 変更なし（`View.Filter` の適用／復元） |
| 4 | フォルダー移動時の自動適用 | `Application_Startup` での初期アタッチ＋初回フォルダーへの再適用を追加。`clsExplorerWatcher` が拾うのは `Explorer` 個別の `FolderSwitch` である点を明記 |
| 5 | 安全な復元機能 | フェーズ0診断の結果（`Save`要否）に応じて実装範囲を確定 |

## 改訂版：用意する操作マクロ

原案の6つに加えて以下を追加：

* `状態確認：管理対象一覧` → 各エントリの **有効／Entry ID無効** を明示するよう拡張
* （QATへの手動登録手順は別紙の導入ガイドとして用意し、マクロとは別に扱う）

## 改訂版：検証計画

1. **（新規・最優先）** 1フォルダーだけで `View.Filter` 変更 → `Save`なしで
   画面に反映されるか、他フォルダーへ波及しないかを確認
2. `NTAN` と `Flags` の2フォルダーで登録・専用ビュー化・未読モードを試験
3. フォルダー往復、**Outlook再起動直後の初回フォルダー表示**、未読／すべて
   切替を確認（原案は「再起動」はあったが「起動直後の初回フォルダー」への
   自動適用確認が抜けていた）
4. 2枚目のOutlookウィンドウを開いた状態での同期確認（`clsExplorerWatcher`）
5. 元の検索条件と件数が壊れていないこと、他の未登録フォルダー（受信トレイ等）
   が無傷であることを確認
6. 合格後、残りのお気に入り検索フォルダーへ展開
7. 緊急復元マクロで元ビューへ戻せることを確認
8. QATへのマクロ手動登録手順の動作確認

## 結論

設計思想（検索条件不変・表示モードのみ全体制御）自体は良い。ただし
「ビューの共有スコープ」と「`Filter`変更の反映条件」という、Outlook側の
未確定要素を先に潰しておかないと、フェーズ2〜5の実装がその場しのぎになり、
最悪「登録していないフォルダーの表示まで変わった」という事故につながる。
フェーズ0（専用ビュー化）を先頭に追加し、フェーズ4のイベント配線を
`Application_Startup` 起点で明確化すれば、原案の骨格はそのまま活かせる。
