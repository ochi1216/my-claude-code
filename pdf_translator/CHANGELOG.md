## [20260812_01] - 2026-08-12

**追加ファイル:** `pdf_translator_20260812_01.py`, `tests/test_pdf_translator_20260812_01.py`

**更新ファイル:** `requirements.txt`, `run_pdf_translator.bat`, `README.md`
（いずれも旧バージョンのファイルは残さず直接更新）

会社PCからGemini APIへの直接アクセスが遮断された（2026-08-10頃）ことへの対応。共通モジュール
`gemini_client.py` の `generate_advanced()` を経由し、直接呼び出しが失敗したら自宅PCのプロキシへ
自動フォールバックする方式へ移行した（`rtocs_organizer` / `analog_ic_se_strategy_organizer` /
`outlook_total_organizer` / `excel_translation` と同じ方式）。

- **本ツール固有の事情（先行4ツールとの最大の違い）**: 旧版は起動時の `init_gemini()` で
  `genai.list_models()` を呼んで使用可能モデルを自動検出していた。これはネットワークアクセスを
  伴うため、遮断下では必ず例外になり「API初期化エラー」ダイアログを出して `sys.exit(1)` していた。
  つまり本ツールは、移行しない限り**起動すらできない**状態だった。自動モデル検出は廃止し、
  固定モデル名を使う方式へ変更した。
  - **副作用（申し送り）**: モデル名を自動で拾わなくなるため、指定モデルが使えない環境では404が
    出るようになる。既定の `gemini-2.5-flash` は他4ツールで実績があるため実害はまず無いが、
    将来モデル名が変わった場合は手で更新が必要。環境変数 `GEMINI_MODEL` で上書きできる。
- 旧SDK `google.generativeai` への依存を廃止した。`genai.Client` と同じインターフェースだけを持つ
  薄い互換シム（`_CommonGeminiClient`）を1つ用意し、クライアント生成箇所だけを差し替えている。
  これにより、レスポンス解析（`[番号] 訳文` の正規表現パース）・3回リトライ・3バッチ連続エラーでの
  フェイルファスト・進捗表示のロジックは一切変更していない。
- `safety_settings`（BLOCK_NONE ×4）は、REST APIの `safetySettings` としてpayloadへ載せるように
  した。載せ忘れると資料の内容によっては応答が空になり、「一部のバッチだけ翻訳されない」という
  切り分けにくい症状になるため、シム側で明示的に転送している。
- 空応答の判定に使っている `response.parts` を維持するため、シムのレスポンスにも `.parts` を
  持たせた（空応答なら `[]` を返すので、従来の「空なら `ValueError` を投げてリトライ」という挙動が
  そのまま保たれる）。
- **挙動差**: `request_options={"timeout": 40}` は共通モジュールに同等の機能が無いため削除した。
  タイムアウトは `gemini_client.py` 側の固定値（直接15秒／プロキシ60秒）になる。遮断下では最初の
  バッチだけ直接呼び出しの15秒タイムアウトを待つぶん遅くなるが、一度失敗すると以降はプロキシ直行に
  なるため2バッチ目以降は影響しない（**仕様どおりの挙動であり、不具合ではない**）。
- `requirements.txt`: `google-generativeai` を削除し、`requests` を追加した（`gemini_client.py` が
  使用する）。`run_pdf_translator.bat` は専用のvenvを作ってここに書かれたものだけを入れるため、
  `requests` を書き忘れると起動はするがAI呼び出し時に失敗する。
- `run_pdf_translator.bat`: `GEMINI_API_KEY` が空のときだけ警告して `pause` で止まっていたが、
  プロキシ専用構成（`GEMINI_API_KEY` は空で `GEMINI_PROXY_URL` のみ設定）でも正常なため、
  **両方が未設定のときだけ**警告するよう変更した。変更は3箇所のみで、ASCIIのみという制約
  （`[20260722_02]` 参照）も維持している。
- **PDFのレイアウト処理は1行も変更していない。** 罫線グリッド検出・ブロック抽出・墨消し・再配置・
  背景色サンプリング等、v02〜v08で積み上げた調整はそのまま。ASTによる関数単位のハッシュ比較で、
  27個の関数・クラス（`_analyze_page_graphics` / `extract_translatable_blocks` /
  `apply_translations_to_pdf` / `_expand_box_safely` / `sample_background_color` /
  `parse_page_spec` / `translate_super_fast_parallel` など）が旧版と**完全一致**することを確認済み。
  変更したのは `check_dependencies` / `init_gemini` / `translate_batch_gemini` の3つだけ。
- 検証用に `tests/test_pdf_translator_20260812_01.py`（75項目）を追加した。偽の `gemini_client` を
  差し込んでpayloadを捕捉する方式で、実際のGemini APIに接続せずに検証できる。PyMuPDFは本物を
  使い、合成PDF（罫線つき表＋色付き棒グラフ＋自由段落）を生成してエンドツーエンドで確認している。
  - **旧版と新版に同じ翻訳文を与えると、出力PDFの図形・テキストが完全一致する**ことを確認済み
    （＝PDF出力への影響がゼロであることの直接的な証拠）。
  - `init_gemini()` がネットワークアクセスなしで成功すること（ソケット生成を禁止した状態で検証）。
  - `safetySettings` が4カテゴリ分そのまま載ること、`temperature: 0.1` が `generationConfig` へ
    camelCaseで載ること、`model` が明示的に渡ること。
  - 空応答・通信失敗時に3回リトライして原文へフォールバックすること、3バッチ連続エラーで
    フェイルファストすること。
  - 認証情報の判定4パターン（**プロキシURLのみでも通る**ことを含む）。
  - 共通モジュールの探索が「2つ上が `common`」という会社PCの配置で正しく解決すること。
- **未検証（実機確認が必要）**: Linuxコンテナからは共通モジュールにも自宅PCプロキシにも到達
  できないため、**実際にプロキシ経由で応答が返るところは未確認**。会社PCでの確認をお願いします。

## [20260722_04] - 2026-07-22

**追加ファイル:** `pdf_translator_20260722_04.py`

v03で「日本語に翻訳されているページとされていないページのバラつきが大きい」という
不具合が実際の資料PDF（v03で修正した24ページの人事survey資料と同一ファイル）で
確認されたため、原因を特定して修正。

- **原因**: 「表・グラフに重なるテキストを保護する」オプションが既定でONだった。
  このオプションは、罫線グリッドとして認識できない図形（画像・チャート等）に矩形が
  少しでも重なるテキストを一律で保護（未翻訳のまま）する仕様のため、タイトルページの
  色帯や、グラフの棒グラフの上に書かれた文字など、実際には翻訳しても問題ない箇所まで
  広く保護対象になってしまい、ページによって翻訳される/されないが極端にバラついていた
  （実データで検証したところ、24ページ中8ページが完全に未翻訳のまま出力されていた）。
- **対策**: v03で墨消し（redaction）自体が表・グラフを破壊する根本原因（罫線誤検出）を
  修正済みであり、図形に重なるテキストを翻訳しても、v03の3段階の安全策により表・
  グラフの構造そのものが壊れるリスクは大幅に下がっている。そのため、GUIのチェック
  ボックス（および関数のデフォルト引数）を「保護する（ON）」から「保護しない
  （OFF、翻訳する）」に変更した。安全性を最優先したい場合は、引き続きチェック
  ボックスをONにすることで、v01〜v03と同様の保護動作を選択できる。
- 実際の資料PDFで、修正前は全く翻訳されなかった8ページすべてに翻訳が適用され、かつ
  罫線の座標は翻訳前後で完全一致（表・グラフの構造は壊れない）ことを確認済み。

## [20260722_03] - 2026-07-22

**追加ファイル:** `pdf_translator_20260722_03.py`

v02で「表・グラフが完全に消失し、PDF生成に失敗する」という致命的な不具合が実際の資料
（棒グラフ付き表を含む24ページの人事survey資料PDF）で確認されたため、原因を特定して修正。

- **根本原因**: v02の罫線グリッド検出は、ページ全面を覆う背景矩形やヘッダー帯の「辺」も
  罫線候補として拾ってしまっていた。実データでは、背景矩形の辺とヘッダー帯の境界線が
  偶然「交差」と判定され、ページのほぼ全域（面積100%近く）を覆う1つの巨大な"セル"が
  生成された。そこに該当ページの全テキストが1つの翻訳単位として飲み込まれ、単色で
  墨消し→再配置されたことで、色付きの棒グラフ・帯・区切り線がすべて上から塗り潰されて
  消失していた（「位置がズレる」どころか、内容そのものが失われる状態）。
- 3段階の安全策を追加:
  1. 罫線候補として採用するのは太さ3pt以下の「細い」矩形の辺のみとする（背景の色
     ブロックや棒グラフの塗りつぶしのような太い矩形は、罫線ではなく図形そのものと
     みなして除外）。
  2. 縦横それぞれに"内部"の区切り線が実質2本以上（＝外枠だけでなく本当に複数列・
     複数行に分かれている）場合のみ表として扱うよう厳格化。二重ストロークで描かれた
     外枠（近接した2本の線が実質1本の線であるケース）は1本に統合してから本数を数える。
  3. 1セルあたりの面積がページ面積の30%を超える場合は採用しない上限を追加。
- 実際の資料PDFを用いて、修正前は完全に消失していた棒グラフ・帯・罫線がすべて保持
  されることを確認済み。また、合成テスト用の罫線つき表（2列×3行）でセル単位の翻訳が
  引き続き正しく機能することも確認済み（今回の厳格化で正規のケースが壊れていないこと
  を検証）。

## [20260722_02] - 2026-07-22

**追加ファイル:** `pdf_translator_20260722_02.py`

**更新ファイル:** `run_pdf_translator.bat`（バグ修正、旧バージョンのファイルは残さず直接更新）

- `run_pdf_translator.bat` をダブルクリックしても「コマンドプロンプトが一瞬表示されて
  消えるだけで何も起こらない」不具合を、2段階で修正。
  - 1回目の修正（括弧ブロックの外に日本語を出すgoto方式への書き換え）では解消せず、
    実機でのエラーメッセージ（`'縺ｮ螟厄ｼ・oto' は、内部コマンドまたは外部コマンド...`
    という文字化け）から、真因を特定した。
  - **真因**: 日本語Windowsのcmd.exeは`.bat`ファイル自体をShift-JIS(CP932)として
    読み込むが、このファイルはUTF-8で保存されていた。UTF-8の日本語1文字（3バイト）を
    CP932の2バイト文字として誤読すると、バイトの対応がズレていき、直後の`goto`や
    `echo`といった英単語の先頭バイトまで巻き込んで破壊してしまう（例: `goto`が`oto`
    に化ける）。`chcp 65001`はコンソール出力の文字コード設定であり、バッチファイル
    自体の構文解析には影響しないため効果がなかった。
  - **対策**: バッチファイル内の文字列をすべて英語(ASCII)に置き換え、日本語を一切
    含まないようにした。これによりWindowsのロケール・コードページ設定に一切依存
    せず、どの環境でも確実に動作する（`chcp 65001` は効果がないため削除）。

v01で報告された「表やグラフの位置がズレる」問題への対策。原因を2つ特定して修正した。

- **原因1**: PyMuPDFの墨消し(redaction)はデフォルトで、矩形に重なる罫線・ベクター図形・
  画像も消去し得る設定だった。→ `apply_redactions(images=PDF_REDACT_IMAGE_NONE,
  graphics=PDF_REDACT_LINE_ART_NONE)` を指定し、表罫線やグラフの図形要素そのものは
  一切消去・上書きしないよう変更（古いPyMuPDFでは自動的にデフォルト動作へフォールバック）。
- **原因2**: 翻訳文を常に左寄せで再配置していたため、元がセンター/右寄せの表セル
  （数値列など）ではズレて見えていた。→ ページの罫線（水平・垂直の直線）から実際の
  表グリッド（セル境界）を検出し、セルの矩形と元の寄せ（左/中央/右、罫線とテキストの
  間隔から推定）を復元したうえで、セル内部だけを墨消しして翻訳文を差し込むよう変更
  （罫線そのものには一切手を加えない）。
- 罫線グリッドの検出は、線分同士が実際に交差しているかで連結成分をクラスタリング
  （Union-Find）して行う。単純に「ページ内の全水平線・全垂直線」を1つの座標集合として
  扱うと、離れた場所にあるグラフの辺（棒グラフの左右の辺など）まで表の列線と誤認識し、
  無関係な座標同士が組み合わさってセルがズレる不具合を開発中に確認・修正した。
- 単一の矩形（棒グラフ1本等）は4辺が互いに交差するため「1マスの表」と誤検出されやすい。
  これを除外し、実際に2マス以上のセルが生まれるグリッドのみを表として扱うよう限定。
  （これが漏れていた場合、チャートの凡例テキストが誤って"表セル"として扱われ、保護
  されずに翻訳・再配置されてレイアウトが崩れる不具合があった＝開発中に確認・修正済み）
- 罫線グリッドとして認識できない図（グラフ・チャート・画像）に重なるテキストは、既定で
  「保護」し翻訳せず原文のまま残す（GUIのチェックボックスでON/OFF切り替え可能）。
- テキストのブロック抽出をPyMuPDFの「ブロック」単位からスパン単位に変更し、表の同じ行
  にある隣接セル（例: 左列と右列）のテキストが1つのブロックとして誤って結合され、列を
  跨いで翻訳・配置されてしまう不具合を修正（開発中のテストで発見・修正）。
- 上記すべての修正を、合成テスト用PDF（表＋チャート＋自由段落の混在ページ）を実際に
  生成してエンドツーエンドで検証済み。罫線の座標は翻訳前後で完全一致（1px も動かない）
  することを確認した。
- GUIに「表・グラフに重なるテキストを保護する（推奨）」チェックボックスを追加（既定ON）。
