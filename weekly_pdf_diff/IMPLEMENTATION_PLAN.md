# IMPLEMENTATION_PLAN.md — weekly_pdf_diff

対象: Weekly Report PDF・前週差分の青太字化ツール
作成: S01（2026-07-29）／ベース資料: 引継ぎ資料（ChatGPT作成構想）＋実PDF調査結果

## 0. この計画の位置づけ

引継ぎ資料の構想を、実際にアップロードされたPDF（89ページ、`Hello_Ochi_San.pdf`
相当）をPyMuPDFで直接調査した結果に基づいて磨き直したもの。特に「表は罫線付き
グリッドではなく疑似構造化テキストである」という発見により、引継ぎ資料が前提と
していたテーブルパーサー中心の設計は不要と判断し、**セクション階層＋行単位比較**
という、より単純な構造に作り替えている。可能な限りシンプルな構成を志向し、
モジュール数・抽象化を引継ぎ資料の原案より意図的に減らしている（詳細は6章）。

### 重要な差異（引継ぎ資料 vs 実データ）

引継ぎ資料は「Weekly数15件、最古2026-04-17、差分処理対象14件」としているが、
実データには2026-04-17より1週古い ww15（2026-04-10）が存在する（合計16ブロック）。

**採用する解釈（初期値）**: 基準日は引継ぎ資料の指示通り **2026-04-17固定**。
ww15（2026-04-10）はWeekly境界検出のアルゴリズム上は検出する（ww16の終端を
決めるのに必要）が、**比較・差分描画のスコープには含めない**。これにより
「基準1件＋処理対象14件＝15件」という引継ぎ資料の件数と矛盾なく整合する。
ww15はPDF出力上そのまま（無変更）で残る。→ この解釈が越智さんの意図と異なる
場合は `config`（後述）の `baseline_date` を変更するだけで動作を切り替えられる
ようにする。

## 2. Weekly Reportの区切り判定方法

ページ番号だけでなく **(ページ番号, ページ内Y座標)** のペアで境界を管理する
（実データで境界がページ途中に来ることを確認済みのため必須）。

判定ロジック（`weekly_splitter.py`）:

1. PyMuPDFの `page.get_text("dict")` で全ページの行（line）を `(page_no, y0, text, bold)`
   のリストとして取得する。
2. 各行が次のいずれかに一致したら「Weekly開始候補行」とする。
   - `From: ` で始まる（かつ次行が `Sent: `）
   - `Subject: Weekly Report` を含む
3. 候補行の直前にある `Subject:` 行を境界の正式な開始位置として採用する
   （`From:`/`Sent:`/`To:`/`Cc:`/`Subject:` の5行ブロックの先頭 = 直前の署名との境目）。
4. **PDF先頭（1ページ目の先頭行）は無条件で最新Weeklyの開始位置**として扱う
   （ヘッダーがないケースへの対応。引継ぎ資料5.2節の想定通り）。
5. 各Weeklyの終了位置 = 次のWeeklyの開始位置の直前（同一ページなら同一ページの
   Y座標、別ページなら前ページ末尾）。
6. 検出件数が期待値（設定可能、初期値16 = ヘッダー付き15＋先頭1）と一致しない場合は
   処理を停止し、検出結果をログへ出力する（引継ぎ資料の方針を踏襲）。

## 3. 前週との差分抽出方法

1. 手順1（区切り）で得たWeeklyを日付順（古い順）に並べ替える。
2. `baseline_date`（初期値 2026-04-17）以降のWeeklyのみを処理対象とする。
   `baseline_date` より古いWeekly（例: ww15）は分割には使うが処理対象外。
3. 各処理対象Weekly $W_i$ について、日付順で直前のWeekly $W_{i-1}$ と比較する
   （PDF上の物理的な前ページではなく、必ず日付順の直前）。
4. 比較は5章「セクション解析」で得た階層構造の対応する項目同士で行う。

## 4. 表・通常文章・箇条書きの比較方法

実データには罫線付きグリッド表が存在しないため、引継ぎ資料が想定する
「表のセル単位比較（table_parser.py）」は採用しない。代わりに、全てのテキストを
**「セクション階層＋行アイテム」の単一モデルで扱う**（詳細は5章）。

比較単位（`TextUnit`、種別は `unit_type` で区別するのみでモジュールは分けない）:

- `paragraph`: 通常文章（例: Weekly updateの説明文）
- `bullet` / `numbered_item`: `•` や `1.` で始まる箇条書き・番号付き項目
- `field`: `ラベル: 値` 形式の行（例: `Project Milestone: TBD`）— 実データの
  「表」に相当する部分はほぼ全てこの形
- `heading`: Boldフラグ＋既知の見出し語（`Work Plan` / `Weekly update` /
  `Summary Project` / プロジェクト名 / `STR` / `Reliability` / `Others`）

対応付けアルゴリズム（`diff_engine.py`、優先順）:

1. 正規化済みテキストの完全一致（同一セクションパス内を優先、なければ
   Weekly全体で完全一致検索 → 一致すれば `moved` として差分対象から除外）
2. セクションパス（例: `Summary Project > Wheeling > STR`）と項目番号が一致する
   ものを同一項目とみなす
3. RapidFuzzによる類似度（閾値 0.82、`config`で変更可）で対応付け
4. 対応が見つからなければ `added`（新規追加）
5. 前週側だけ残った項目は `deleted`（今週PDFには描画せず、差分レポートにのみ記録）

対応が取れた項目同士は `difflib.SequenceMatcher` で単語単位比較し、
`insert`/`replace` された単語だけを青太字対象にする。対応の信頼度が低い場合
（類似度が閾値をわずかに超えただけ、など）は単語差分を無理に作らず、
**行アイテム全体を青太字化**する（引継ぎ資料 4.2節の方針を踏襲）。

除外対象（比較しない）: メールヘッダー（From/Sent/To/Cc/Subject）、署名ブロック、
ページ末尾のOneNoteフッター行（フォント`YuGothic-Regular`かつ末尾が「ページ」の行、
または正規表現 `\d{4}_\d{2} - \d+ ページ`）、固定の挨拶文
（`Hello Ochi San.` / `Please refer to my weekly report as follows.` / `Thank you.` /
`Regards`）。

## 5. セクション解析（`sectionize.py`）

Weekly1件分の行リストから、以下の浅い木構造を作る（過剰な汎用化はしない。
既知の3大見出し＋プロジェクト単位のみを扱う専用ロジックでよい）。

```
WeeklyReport
├─ Work Plan            (paragraph/bullet の列)
├─ Weekly update
│   ├─ <プロジェクト名>   (Bold見出し, 例: Wheeling / Caracal / Grand Teton)
│   │   └─ numbered_item の列
│   └─ ...
└─ Summary Project
    ├─ <プロジェクト名>
    │   ├─ field: Project Name / Project Milestone / S Gate ... (ラベル:値行)
    │   ├─ STR         (見出し) → numbered_item の列
    │   ├─ Reliability (見出し) → numbered_item の列
    │   └─ Others      (見出し) → numbered_item の列
    └─ ...
```

分類ルール:

- 見出し判定 = Boldフラグ **かつ** 既知語リストに一致（`Work Plan`, `Weekly update`,
  `Summary Project`, `STR`, `Reliability`, `Others`, および `Summary Project` 配下で
  最初に現れるBold単語をプロジェクト名として登録）。
- プロジェクト名リストは実データからハードコードせず、`Summary Project`セクション内で
  最初に出現するBoldの短い行を都度プロジェクトとして動的登録する（新規プロジェクトの
  追加に自動対応するため）。
- 異なるセクションパスの項目同士は対応付けの候補にしない（4章の誤対応防止）。

## 6. 青太字をPDFへ反映する方法（`render.py`）

1. 差分対象単語の座標を `page.get_text("words")` で取得（今週側PDF上の座標）。
2. **元文字の消去**: `page.draw_rect()`による見た目だけの上書きは採用しない
   （下に元の文字データが残ったままになり、テキスト抽出・検索・コピーで
   新旧の文字が二重に取得されてしまうことをPhase 4実装時に確認）。代わりに
   PyMuPDFの正式なredaction機能（`add_redact_annot(rect, fill=背景色)` →
   `apply_redactions()`）を使い、文字データそのものを除去してから背景色で
   塗りつぶす。背景色は白固定にせず、矩形直近の塗り情報（`page.get_drawings()`）
   から判定する（実データに薄い青 `#C1E4F5` 相当の帯が存在することを確認済みの
   ため必須）。罫線を壊さないよう矩形は文字領域よりわずかに内側に取る。
3. 消去した位置へ同じテキストを **色 `#0033A0`（濃い目の青）・太字** で再描画する。
   引継ぎ資料の初期案 `#0057B8` は実データの既存リンク色 `#0066CC` に近すぎるため、
   より濃い青にずらして視認性を確保する（4.3節参照。config で変更可能）。
4. フォントは元がArial系のため `Helvetica-Bold`（PDF標準フォント）で代替する
   （実データに専用の埋め込みBoldフォントは無く、Arial,Boldも標準フォント相当のため
   互換性上の問題は小さいと判断）。
5. 太字で幅が広がる場合は (a) 水平方向のみ縮小 → (b) フォントサイズを最大10%縮小 の順で
   調整する。
6. **リンク注釈とredactionの相互作用（Phase 4実装時に発見した重要な落とし穴）**:
   `apply_redactions()` は、redaction矩形と重なるリンク注釈を**一緒に削除して
   しまう**（PyMuPDF 1.28 / MuPDF 1.29で実機確認済み）。「リンク注釈を削除せず
   維持する」という要件と直接衝突するため、`render.py`ではredaction適用前に
   そのページのリンク一覧を取得し、redaction矩形と重なるものだけをredaction後に
   同じ内容で再挿入（`page.insert_link()`）することでリンクを維持している。
   （`get_links()`は挿入直後の同一セッションでは反映されず、保存→再読込した
   PDFで初めて正しく確認できることもあわせて確認済み。実際の出力は必ず
   `doc.save()`を経由するため、最終成果物には問題なく反映される。）
7. 削除された文言（前週にのみ存在）はPDFには描画せず、差分レポート
   （CSV/HTML）にのみ記録する。

## 7. モジュール構成

既存リポジトリの慣習（`rtocs_organizer/`等: フラットなファイル構成、
`ツール名_yyyymmdd_連番.py` のバージョン管理、`src/`レイヤーやpyproject.tomlは
使わない）に合わせる。引継ぎ資料原案（12モジュール、src/レイアウト、
pyproject.toml、table_parser/coordinate_mapper/qa_checker等の専用モジュール）は
本プロジェクトの規模には過剰と判断し、責務を統合して以下に簡略化する。

```
weekly_pdf_diff/
├── IMPLEMENTATION_PLAN.md
├── README.md
├── CHANGELOG.md
├── requirements.txt
├── weekly_pdf_diff_20260729_01.py   # CLIエントリポイント（argparse、パイプライン統括）
├── models.py                        # WeeklyReport / TextUnit / DiffResult（dataclass）
├── pdf_reader.py                    # PyMuPDF薄いラッパー（行・リンク・背景色の抽出）
├── weekly_splitter.py               # Weekly境界検出・日付抽出（2章）
├── normalize.py                     # 比較用テキスト正規化
├── sectionize.py                    # セクション階層化（5章）
├── diff_engine.py                   # 対応付け＋単語差分（4章）
├── render.py                        # 青太字描画（6章）
├── report.py                        # CSV/HTML/JSON差分レポート出力
└── tests/
    ├── conftest.py                  # 合成PDF生成ヘルパー
    ├── test_weekly_splitter.py
    ├── test_normalize.py
    ├── test_sectionize.py
    ├── test_diff_engine.py
    └── test_render.py
```

設定は専用の設定クラス／YAMLスキーマを作らず、CLIエントリポイント内の
デフォルト辞書＋argparseフラグのみで完結させる（`--config path.yaml` で
上書き可能にするが、必須ではない）。これにより引継ぎ資料原案にあった
`config/default.yaml` の固定スキーマ管理コストを避ける。

CLI例:

```bash
python weekly_pdf_diff_20260729_01.py input.pdf \
  --output output/weekly_report_diff_blue_bold.pdf \
  --baseline 2026-04-17 \
  --color "#0033A0"

python weekly_pdf_diff_20260729_01.py input.pdf --analyze-only --output-dir output/
```

出力ファイル（引継ぎ資料11章を踏襲）:
`*_diff_blue_bold.pdf` / `*_weekly_index.json` / `*_diff_report.csv` /
`*_diff_report.html` / `*_processing.log`（デバッグ画像出力は `--debug-images` 指定時のみ）。

## 9. リスクと代替案

| リスク | 対策 |
|---|---|
| ww15(2026-04-10)の扱いが越智さんの意図と異なる可能性 | `baseline_date` をconfigで即切替可能にする。次回セッションで確認事項として提示 |
| 差分色`#0057B8`が既存リンク色`#0066CC`と近い | `#0033A0`へ変更し、太字も必須の識別要素とする |
| 背景が白固定でない（薄青帯・濃青ブロックあり） | 消去前に矩形周囲の塗り情報を実際にサンプリングする（6章2.） |
| 罫線表を前提にすると過剰設計になる | セクション＋行アイテムの単一モデルに統一（4-5章） |
| 太字で文字幅が広がりセル外にはみ出す | 水平縮小→フォントサイズ縮小の順で調整、それでも収まらない場合は警告ログ |
| 対応付けミス（誤って別項目を同一視） | セクションパス一致を対応付けの必須条件にする |
| 大幅書き換えで単語差分が破綻 | 信頼度が低い場合は行アイテム全体を青太字化 |
| 罫線なし複数列の疑似テーブル（STR/Others配下の進捗ステータス表等）が行・セル単位で再構成されない | `Line.x0`による継続行判定でテキストの誤結合（別列の混入）は防止済み。ただし行・列としての意味的な再構成は未実装のため、これらの領域は断片単位の`TextUnit`となり、差分の対応付け精度は本文の箇条書き・番号付き項目に比べて低い。列クラスタリングによる行復元は将来フェーズの課題とし、S01では「誤って青太字にしない」を優先し、対応が取れない断片は`added`（新規）またはセクション内fuzzy一致に委ねる |
