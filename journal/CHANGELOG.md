# CHANGELOG

## v1.32.0 - 雨をディシジョン・ジャーナルの要件に合わせる（forecast.py / forecast_ui.py）
- 背景: この機能は**リスク管理ではない**という位置づけの追記を受けての対応。
  リスクは10個併記しても誰も困らないが、Forecastは1つに絞った瞬間に外れが
  確定する。「選ばされること」と「後で採点されること」が存在理由なので、
  そこを緩めるとただのリスク一覧がもう一つ増えるだけになる。
  Tetlock『超予測力』/ Annie Duke『Thinking in Bets』のディシジョン・
  ジャーナルが下敷きで、実装に直結する結論は「結果だけを見ても上達しない。
  理由を書き、理由が外れたのかを確認した人だけが上達する」
- **① 1レコード1予測**: 雨の入力を複数行Textから**1行のEntry**に変更した。
  「AまたはB」を並べて書けると何をもって外れとするかが決まらないため。
  あわせて、ヘッジ・併記の表現（可能性 / かもしれ / と思う / または /
  改行 等）を検知したら一度警告を出すようにした。**保存自体は止めない**が、
  気づかないまま溜まると後で採点できなくなるため一度気づかせる。
  Entryは手入力では改行できないが**貼り付けでは入り得る**ことがテストで
  判明したので、保存値は必ず1行に正規化し、改行も併記として検知する
- **③ 予測の当否と理由の当否を分離**: 従来は1つの結果＋4択の診断に
  混ぜていたものを、**○×△を2つ**（①予測は当たったか ②理由は合っていたか）
  に分けた。「予測○・理由×」＝たまたま当たっただけ、が最も学びの大きい
  ケースで、1つにまとめると見えなくなる（結果が当たっていてもモデルは
  壊れたままなので次に大きく外す）。`is_lucky_hit()` で単独に数えられる
  ようにし、一覧では赤字＋件数で表示する。組み合わせの読みラベルは
  `describe_result()` で導出する（保存はあくまで2つの値）
- **④ 保存後、空・雨・理由を凍結**（最重要）:
  「編集する関数を作らない」だけでは、後で不用意に書き換える経路を
  足せてしまう。`_update()` が `FROZEN_FIELDS` の前後を比較し、1つでも
  変わっていたら**保存せずに `FrozenFieldError` を投げる**ようにした。
  後知恵バイアスで「まあそうなると思っていた」に書き換わると、外れが
  記録に残らず、この機能の目的が丸ごと失われるため。
  訂正は新設の `append_note()` による**追記のみ**で、元の文言は必ず残る。
  確認期日は延期の運用があるので凍結対象外
- **⑥ 削除手段を持たない**ことを明文化した。外した予測の記録こそが資産で、
  消せると当たったものだけが残る。判定できなくなった雨は
  `mark_unjudgeable()` で終了させ、記録自体は残る
- **確信度を任意に**変更した（既定値つきで実質必須だったものを空欄可に）。
  最初から重くすると続かないため。ただし将来のキャリブレーション
  （「70%と書いたもののうち実際に何割が起きたか」を集計して自信過剰か
  過小かを見る）用に **`confidence_pct` の器だけ先に用意**した。後から
  足すとマイグレーションが要るため
- スキーマを v2 に上げ、v1のレコードは読み込み時に自動で補完する
  （旧 `diagnosis` は分かる範囲で「理由の当否」に読み替える）。
  破壊的な変換はしない
- daily_journal_20260807_09.py は**変更なし**（呼び出す関数の名前・引数が
  変わっていないため）。v1.31.0で配置済みならそのままでよい
- 動作確認: データ層(44件+37件)・UI(32件+13件)に加え、v1.30.0のTIME/LKPT
  分離と自動クローズの回帰も含めて**10スイート全て**を通した。特に
  ①雨・空・理由の書き換えが例外で止まりファイルが変わらないこと
  ②確認期日の変更（延期）は通ること③追記が時刻つきで積まれ元の本文が
  無傷なこと④予測○/理由×が「たまたま当たった」として拾えること
  ⑤4通りの組み合わせが区別できること⑥ヘッジ表現で一度止まり二度目で
  保存されること⑦断定なら一度で通ること、を実測で確認した

## v1.31.0 - 「雨（予測）」の記録と答え合わせを追加（forecast.py / forecast_ui.py / daily_journal_20260807_09.py）
- 要望: 空・雨・傘の枠で見ると、既存機能は空（教訓・K/P）と傘（タスク・T）
  しかなく、**雨（この先どうなると見るか）の席が構造的に無い**。KPTのK/Pは
  過去の観測、Tは次の行動なので三つとも空か傘にあたる。予測を書き留めて
  いない経験は複利で積まれない（後知恵バイアスで「そうなると思っていた」と
  記憶が書き換わり、外したことに気づけないため）ので、日付つきの断定を
  残したい、という要望
- **この機能の目的は「予測を書くこと」ではなく「後から答え合わせが必ず
  行われること」**。そのため設計上の優先順位も、入力のしやすさより
  答え合わせが確実に回ることを上に置いた
- 対応（forecast.py 新規／データ層）:
  - 保存先は `journal_data.xlsx` と分けて **`forecasts.json`**（同じフォルダ）。
    理由は①まだ形が固まっておらず、列追加に自己修復マイグレーションが要る

    並べ替えた瞬間にIDが壊れる（Actionsが抱えている弱点と同じ）③毎時の
    タイムログ保存に巻き込まれない④外部プロセスからロック無しで読める
    （morning_brief.py 連携用。実装は今回不要とのことなので読める形まで）
  - IDは `R-YYYYMMDD-NN`。書き込みは一時ファイル経由で置き換えるため、
    途中で落ちても既存の記録が壊れない
  - **確信度**（たぶん/おそらく/ほぼ確実）を追加。55%で外した（正常）と
    95%で外した（読みが壊れている）を区別できないと較正に使えないため
  - **外れ方を構造化**した。特に「予測は当たったが理由が違った」を選択肢に

    違えばモデルは壊れたままなので次に大きく外す。数えられる形にした
  - 出口として **延期**（回数を記録）と **判定不能** を用意。○×△しか出口が
    無いと、判定できない雨に対して嘘をつくか無視するかになり、無視が
    始まった時点で仕組みが死ぬ。延期回数は事務データではなく測定値で、
    何度も延期される予測＝反証可能な形で書けていなかった、という学びになる
- 対応（forecast_ui.py 新規／画面）:

  - **答え合わせ画面が起動時に向こうから出てくる**。人は自分から見返さない
    ため。ただし毎時のポップアップに混ぜると1日11回になり確実に無視される

    習慣化するため**古い順に最大3件**だけ出す（総数は別に表示する）

  - ダッシュボードには**意図的に組み込んでいない**。形が固まらない段階で

- 対応（daily_journal_20260807_09.py）:

## v1.30.0 - TIME / LKPT / タスクの3機能を分離（storage.py / daily_journal_20260807_08.py / dashboard.py）
- 要望: 目的の違う3つの記録が1つの「登録」ボタンに融合していた。期間
  （何時から何時まで）が必要なのはタイムログだけで、LKPTとタスクは
  タイムスタンプさえあればよい。にも関わらずLKPTはタグを選ばないと記録
  できず、「思いついた振り返りを書き留めるだけ」ができなかった。
  タスクと同じく「開いて・書いて・Enter」で完結させたい、という要望
- 「登録ボタンはいつ使うのか」への回答: **廃止した**。TIMEはタグを押した
  時点、LKPTとタスクはEnterの時点でそれぞれ即記録されるため、このボタンに
  残された仕事が無くなった。あわせて「記録すると画面が消えて訂正できない／
  画面を残すと毎回手動で閉じる手間が増える」というジレンマに対しては、
  **記録後3.5秒で自動的に閉じ、何か操作するとタイマーが止まる**方式で
  両立させた（タグ・中項目の操作では数え直し、LKPT欄やタスク欄に触れたら
  恒久的に停止するので、文章を書いている途中で閉じることはない）。
  結果、通常のチェックインは「タグ→中項目」の2クリックのみで、閉じる
  操作は不要になった（従来は登録ボタンを含めて3クリック）
- 対応（storage.py／既存関数は変更せず追加のみ。過去のdaily_journal_*.pyが
  `record_check_in()`に依存しているため）:
  - `append_time_log()` … TimeLogにのみ記録し、書き込んだ行番号を返す
  - `update_time_log_row()` / `delete_time_log_row()` … 直前の記録の修正・
    取り消し。開始・終了が期待値と一致しない限り書き換えない**楽観ロック**を
    入れた（Actionsシートが行番号をIDにしていて、Excelを直接編集すると
    別の行を壊すという既存の弱点を、TimeLogでは繰り返さないため）
  - `append_lkpt_entry()` … Entriesにのみ記録する。タグは空文字可。
    旧形式（日付/タグ/メモの3列）からの移行`_ensure_lkpt_columns()`は
    これまで`record_check_in()`からしか呼ばれていなかったため、新経路でも
    必ず通すようにした
  - `_compute_time_range_v2()` … 当日まだ記録が無い場合、**勤務開始時刻
    (`WORK_START_TIME`、既定08:00)を起点にする**。従来は0分の「基準点」
    だったため、8時から働いて9時に初記録すると1時間が消えていた。
    また上限(2時間)を超えて空いた分は、黙って捨てず**「未記録」タグの行**
    として残すようにした（従来は9:00→15:00で4時間が無言で消滅していた）
- 対応（daily_journal_20260807_08.py）:
  - タグを押した瞬間にTimeLogへ記録し、以降の中項目クリックや別タグの
    クリックは**追記ではなく同じ行の上書き修正**にした（5分以内）。これが
    無いと、押し間違い→正しいタグを押す で「誤ったタグが実作業時間を保持し、
    訂正のクリックは0分の行になる」というデータの取り違えが起きる。
    同じタグをもう一度押すと記録ごと取り消す。修正可能な行番号はウィンドウを
    閉じても保持するため、閉じた直後に開き直しても訂正できる
  - 「Other」の自由記述はEnterでもフォーカスが外れた時でも確定するように
    した。またタグを押した時点で既に有効な記録になっているため、
    「Otherだけ確定操作が別」という非対称と、中項目が未設定のタグが
    行き止まりになる問題が、どちらも構造的に消えた
  - LKPTはどの欄でEnterを押しても、L/K/P/Tをまとめて**1行**として記録する。
    タグは不要（選択中なら引き継ぐかをチェックで選べる）。記録後も
    ウィンドウは閉じず、続けて何件でも書ける
  - 「✅登録」を廃止して2ボタンに。「❌」は記録を取り消さないため
    「✖（閉じる）」に改称した
- 対応（dashboard.py）:
  - **TIMEモードに中項目を表示**した。これまで`storage.py`が書き込む
    だけで`dashboard.py`は一度も読んでおらず、「R19の中で何をしていたか」
    という中項目導入の目的が達成されていなかった
  - タグを`or ""`で正規化。タグ無しLKPTが常態になるため、COACHのプロンプトに
    文字列`None`が混入する不具合を塞いだ（AIが「None」を実在のタグと
    誤解するのを防ぐ。代替語も入れない）
  - 「未記録」タグに灰色を割り当て、グラフ・一覧で「埋まっていない時間」
    として見えるようにした
- 動作確認: ロジックテスト43件（storage）・22件（dashboard）・29件（popup）と
  自動クローズの実測11件を全て通した。特に①押し間違いの訂正で0分の行が
  生まれずTimeLogが1行のままであること②修正可能時間を過ぎたら追記に
  切り替わること③楽観ロックが不一致時にファイルを一切書き換えないこと
  ④LKPT記録後に2件目が黙って消えないこと（タスク欄で起きたv1.22.1と同種の
  バグの再発防止）⑤放置で閉じ・操作で閉じないこと、を実測で確認した。
  画面はXvfbで7状態、ダッシュボードのTIMEモード（中項目・未記録の表示）も
  スクリーンショットで確認済み

## v1.29.0 - LKPTアコーディオンを開閉しても上端の位置がずれないように変更（daily_journal_20260807_07.py）
- 要望: LKPT欄のアコーディオンを開くと、ウィンドウの上端（タイトル・
  タグ一覧・LKPTボタン）の位置がずれてしまう。開いても上端は動かさず、
  下端（LKPT入力欄より下）だけが動くようにしてほしい
- 原因: `_resize_window()`が、ウィンドウの下端を「画面下端から80px」に
  固定する計算式（`y = screen_h - height - 80`）で上端(y)を毎回
  求め直していたため、高さが変わるたびに上端が上下に動いていた
  （開けば上端が上へ、閉じれば下へ移動する仕様になっていた）
- 対応:
  - `_resize_window()`を、現在の上端(y)をそのまま使う（毎回計算し
    直さない）方式に変更した。ただし、それによって下端が画面をはみ出す
    場合に限り、はみ出さない範囲でyを上にずらすフォールバックを残した
  - 初回表示時の上端位置(`show()`内のy計算)も、畳んだ状態の高さではなく
    「展開した時の高さ」を基準に決めるよう変更した。畳んだ状態基準の
    ままだと、展開時に画面下端をはみ出さないよう結局yを動かす必要が
    生じてしまうため、あらかじめ展開後の高さぶんの余白を確保しておく
    ことで、開閉時にyを動かさずに済むようにしている（結果として、畳んだ
    状態のポップアップは以前よりやや高い位置に表示される）
- 動作確認: Xvfb上で、1920x1080相当の画面では①畳んだ状態→開く→
  再度畳む、の一連の操作で上端(y)が一切変化しないことを実測で確認した。
  また1024x768相当の狭い画面でも、上端が画面内にクランプされたまま
  開閉できることを確認した。あわせて、タグの選択/選択解除・タグチップの
  列揃え・アクション一覧（★優先/○完了/Enter登録/スクロール等）に
  変更が無いことも再確認した

## v1.28.0 - タグチップの列ズレ修正・LKPTボタンを全幅に（daily_journal_20260807_06.py）
- 報告・要望:
  - タグのチップ列が行ごとに微妙にズレて見える
  - LKPTボタンの横幅を、登録/キャンセル/DBなど他のボタンと揃えたい
- 原因: タグチップを「行ごとのFrame」に分け、各行の中で
  `pack(side="left", fill="x", expand=True)`させていたため、行ごとに
  タグ名の文字幅（"R19" と "JP Site" 等）が違うと、各行が独立に
  余白を再分配してしまい、列の境界（チップの左端・幅）が行によって
  微妙にズレていた
- 対応:
  - タグ一覧を「行ごとのpack」から、`tag_frame`全体を1つの`grid`にまとめ、
    `columnconfigure(uniform="tagcol")`で列幅を強制的に統一する構成に
    変更した（登録/キャンセル/DBの3ボタンで既に使っている
    `uniform="btn"`と同じ仕組み）。これにより、行によらず列の左端・幅が
    完全に一致するようになった
  - LKPTトグルボタンを、中央寄せの小さなピルから`fill="x"`の全幅表示に
    変更し、タグ一覧・登録/キャンセル/DBの行・入力欄と横幅を揃えた
- 動作確認: Xvfb上で、①1列目（R19/NPI）・2列目（JP Site/その他）それぞれの
  チップの`winfo_x()`が行によらず一致すること、全チップの`winfo_width()`が
  完全に一致すること②LKPTボタンの`winfo_width()`がタグ一覧・登録/
  キャンセル/DB行と一致すること、を実測で確認した。あわせて、タグの
  選択/選択解除・アクション一覧（★優先/○完了/Enter登録/スクロール等）に
  変更が無いことも再確認した

## v1.27.1 - 登録/キャンセル/DBボタンのバランス調整（daily_journal_20260807_05.py）
- 報告: v1.27.0でDBアイコンだけ別フォント（size=20）にして大きさを
  合わせようとしたが、結果的に3ボタンの高さがバラバラになり、
