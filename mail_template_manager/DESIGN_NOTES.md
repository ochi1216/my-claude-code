## 1. このツールの位置づけ

### 1-1. 解く課題

越智さんは、毎月の定型メール（Export Report → Jay宛、Over Time Report → Janice宛 等）を
繰り返し手作業で作成している。宛先・件名の型・本文の骨組みは固定で、**変わるのは
その月のSharePointフォルダ／ファイルへのリンクと年月表記だけ**である。

痛みの本体は「SharePointを開いて該当月のフォルダを探し、リンクを取ってくる」こと。
**文面の保存だけなら Outlook 標準のクイック操作／`.oft` で足りてしまう。**

### 1-2. ★重要★ なぜ作るのか（時間の節約では正当化できない）

代替手段（`.oft` ＋ SharePointお気に入り ＋ Power Automateの定期リマインド）と比較すると、
**時間の節約は月2通で年16分**にしかならず、投資を正当化できない。

代替手段が**絶対に到達できない**のは次の1点だけであり、これが本ツールの唯一の存在理由である。

> **定型メールが増えたときに、それらを一覧・分類・棚卸しできること。**

`.oft` が10個、PAフローが10本になった瞬間、「何を誰にいつ送る約束になっているか」が
誰にも分からなくなる。これは要望4（メタデータでソート・フィルタ）そのものであり、
18名・複数機能の提出物を束ねる Site Manager の職責に直結する。

**2026-09-16、越智さんに確認：定型メールは5〜10枚程度。** 判定基準（5枚以上なら作る）に
該当するため Go とした。3枚以下なら作らない方がよいと判断していた。

この帰結として、**M1の一覧画面の主役は「カード」ではなく「今月の提出状況」**とする。
`.oft` も Power Automate も**状態を持たない**ため、「今月これを送ったか？」に答えられるのは
本ツールだけである。実装コストの増分はゼロ（同じデータの見せ方の問題）。

### 1-3. ★重要★ 社内実証記録の正確な読み方（一度誤読した）

`power_automate_safety_checkin/README.md:19` に
「Azure ADアプリ登録・`Mail.Send`権限への管理者同意が必要であり、個人の権限では完結しない」
という記録がある。

**これは Graph の「アプリケーション権限」の話であり、Power Automate の
ユーザー実行フロー（Office 365 Outlookコネクタ）とは別物である。**

設計案 v3.0 ではこれを「Graph経由のメール送信は社内で使えない」と一般化してしまったが、
過剰な一般化だった。正しくは：

- Graph のアプリケーション権限による送信 → **管理者同意が必要（社内で実証済みの壁）**
- Power Automate のユーザー実行フロー → **原理的に可能**（DLPポリシーで Outlook コネクタが
  禁止されていなければ。未確認）

**この帰結として、M3（`schtasks` による定刻実行）の存在価値は相対的に下がる。**
M1の運用実績を見てから、Power Automateとのハイブリッド（本文生成はPython、
定刻配信はFlow）と比較して要否を判断する。

## 2. M0：実機プローブで確かめること

`document_search_manager` 3-6節の「権限が通るか不明だったので、まず診断だけを実装した」
という作法を踏襲する。**最大の未知を、UIを作り込んだ後ではなく最初に測る。**

越智さんの実機時間は**1回しか使えない**前提で項目を選んだ。

| # | 確かめること | これで決まること |
|---|---|---|
| 1 | Outlookへの接続と `Application.Version` | 下書きを直接作る方式（M1-α）が使えるか |
| 2 | `CreateItem(0)` | 同上 |
| 3 | 署名の取得と本文の前方結合、**署名HTMLの実物** | 署名を消さずに本文を差し替えられるか。本文で使えるタグの範囲 |
| 4 | `.Save()`（画面を開かない下書き保存） | **M3の無人定刻実行が成立するか** |
| 5 | 送信元アカウントの構成、`SendUsingAccount` / `SentOnBehalfOfName` | カードに `from_account` が要るか |
| 6 | 日本語フォルダ名・長いURLを含む `<a>` の保持 | 本文へのリンクの持たせ方 |
| 7 | **`UserProperties` の書き込みと保存後の読み取り** | **「未送信」バッジが嘘をつかずに済むか**（後述 2-1） |
| 8 | `.eml` の書き出しと関連付け | 「新しいOutlook」に移行した場合の代替手段（M1-β） |
| 9 | Graph で対象フォルダの子を列挙できるか（実URL） | M1の中核機能 |

**項目9で汎用の `/children` 疎通を測らない理由**：`DESIGN_NOTES`（document_search_manager）
3-6節で 2026-09-10 に会社PCで実証済みのため。越智さんの時間を既知の確認に使わない。

### 2-1. ★重要★ 「送信済み」を件名で照合してはいけない

設計案 v3.0 では、送信済みアイテムを**件名＋宛先で照合**して `sent` を検出する案だった。
**これは実運用で必ず壊れる。** 越智さんは送信前に一言足す（そして件名も直す）。
件名が変われば照合が外れ、**送ったのに「未送信」と表示される**。

**未送信バッジが一度でも嘘をつくと、誰も見なくなる。**
本ツールが掲げる価値（送り忘れ撲滅）が、実装方式のせいで自壊する。

そこで、下書き作成時に `MailItem.UserProperties` へ `MTM_CardId` と `MTM_PeriodId` を
埋め込み、送信済みアイテム側でそれを読む方式とする。**件名も本文も自由に編集されて構わなくなる。**

ただし `UserProperties.Add` が通るか、保存後もプロパティが残るかは**未検証**
（`outlook_total_organizer` は読み取り専用のため前例がない）。M0の項目7で測る。

**失敗した場合の代替**：一覧に「送信しました」チェックボックスを置き、人が1クリックで
状態を進める。自動検出をあきらめる代わりに、**嘘をつかない**。

### 2-2. 署名は `GetInspector` で取る（`Display` ではなく）

Outlook が署名を挿入するのは、メールアイテムの `Inspector` が生成されたとき。
`.Display()` でも挿入されるが**ウィンドウが開いてしまう**。`GetInspector` に触れるだけなら
画面を開かずに済み、**M3の無人実行にも直結する**ため、まず `GetInspector` を試し、
署名が入らなかった場合のみ `.Display()` にフォールバックする。

### 2-3. プローブが守る設計上の制約

| 制約 | 理由 |
|---|---|
| **メールを一切送信しない** | 診断で対外的な事故を起こさない。`Send` を呼ぶコードが存在しないことを `ast` による自動テストで担保している |
| **作成したメールをすべて削除する** | 越智さんの下書きフォルダを汚さない |
| **各項目を try/except で完全に独立させる** | 1項目目で落ちて**情報がゼロになるのが最悪のシナリオ**。「①成功 ②成功 ③失敗（理由）」と全部出す |
| **依存は標準ライブラリ＋win32com のみ**（msal は任意） | 社内プロキシ・証明書の問題で `pip install` が詰まると、**プローブ自体が動かず何も分からない** |
| **結果は UTF-8 BOM付きで書く** | BOM無しだとメモ帳で文字化けし、報告の往復が1回増える |
| **pywin32 未導入は「設計の分岐」と区別する** | 環境を直せば解決する失敗を「M1-βへ切り替え」と誤判定しない。この場合は結果ファイルの送付も依頼しない（往復が1回無駄になるため） |
| **win32com をトップレベルで import しない** | レポート整形・HTML組み立て・例外分離を、開発環境（Linux）で単体テストできるようにするため |

## 3. カードとアルゴリズムの保存形式（M1で実装予定・未実装）

### 3-1. スクリプトではなく宣言的データにする

「その1ショットタイミングで何をどのように更新するか」＝アルゴリズムを、Pythonスニペット等の
**コードとして保存しない**。理由は3つ：GUIから安全に編集できる／壊れたときに原因を追える／
任意コード実行にならない。

代わりに「**変数バインディング表＋テンプレート文字列**」として保存する。
越智さんの例1・例2は、抽象化すると
**「①対象期間を決める → ②その期間でSharePointの場所を特定 → ③テンプレートに差し込む」**
の3段でしかない。

### 3-2. 名前空間の宣言（未定義参照は保存時にエラーにする）

「全フィールドをテンプレート展開する」「未定義参照は保存時にエラー」という2つの原則を
両立させるため、参照できる名前を明示的に決めておく。

| 名前空間 | 公開フィールド |
|---|---|
| `period.*` | `unit, start, end, id, label, year, month, month2, quarter, week` |
| `contacts.*` | `contacts.json` のキー（例 `contacts.jay`） |
| 変数の `render` 内 | `value, display, url, name, meta` を**プレフィックス無し**で参照（**自分自身のResolvedValueに対する局所スコープ**） |

`render` を局所スコープと決めたのは、`{{export_link.name}}` のように**変数が自分自身を参照する**
書き方を排除するため。これを許すと、グローバルな参照解決（2フェーズ評価・未定義チェック・
将来のDAG）と衝突する。

### 3-3. `history` は「実行ログ」ではなく「参照できるデータ」

`history` を実行ログとしてだけ実装すると、将来
「前回は2026/08でした」「Report #12」（`type: "history_ref"`）を足す経路が塞がる。
**`history` は変数から参照できる**という前提で設計すること。

### 3-4. 越智さんの回答で確定した仕様（2026-09-16）

| 項目 | 回答 | 設計への反映 |
|---|---|---|
| 対象期間 | **前月分・暦日の1日** | `period.offset_from_run = -1` / `business_day = false`。**副次効果**：前月分なら対象フォルダは実行時点で既に存在しているはずで、「フォルダ未作成」問題の発生確率が大きく下がる |
| フォルダ未作成時 | **下書きは作らず「まだ無い」とだけ通知** | `on_missing` の既定を `notify_only` に確定。中途半端な下書きが残らない |
| Outlook移行予定 | **通知は来ていない** | M1-α（COMで下書きを直接作る）を主線とする。`.eml` は保険 |
| 定型メールの枚数 | **5〜10枚程度** | Go判定（1-2節） |

## 4. 実機で判明した事実

### 4-1. ★解決済★ 項目[8]（.eml）が正しく開けなかった（2026-09-17）

**症状**：越智さんの会社PCで項目[8]を実行したところ、Outlookは新規メールを開いたが、
件名欄は「(件名なし)」のままで、本文に `Subject: [MTM PROBE] eml test` 等のヘッダー行が
生の文字列として表示された（`.eml` がメールとして解釈されず、プレーンテキストとして
扱われた）。

**原因**：`check_08_eml`（旧実装）が改行を手動で `"\r\n"` として組み立てた文字列を、
**テキストモードで開いたファイルに書き込んでいた**。

```python
with open(eml_path, "w", encoding="utf-8") as fh:
    fh.write("\r\n".join(lines))
```

Windows上のPythonは、テキストモードでの書き込み時に文字列中の `\n` を自動的に
`os.linesep`（Windowsでは `\r\n`）へ変換する。すでに `\r\n` として組み立てていた
文字列の中の `\n` がもう一度変換され、実際にファイルへ書かれる改行は `\r\r\n`
になっていた。RFC 5322（メール形式）は正しい改行を要求するため、Outlookがヘッダー部を
認識できず、ファイルの中身をそのままプレーンテキストとして本文に流し込んだと考えられる。

**このバグは開発環境（Linux）では発現しない**（`os.linesep` が `\n` のため二重変換が
起きない）。既存の検証ハーネスがWindowsのテキストモード書き込みの挙動までは
検証していなかったため、実機で初めて発覚した。

**修正**：
1. 手組みのヘッダー文字列をやめ、標準ライブラリ `email.message.EmailMessage` で
   メッセージを組み立てる（`build_eml_bytes` 関数）。ヘッダーのエンコーディング・
   改行・区切りをライブラリが保証するため、日本語件名のMIMEエンコード崩れ等も
   あわせて防げる。
2. `as_bytes()` で得たバイト列を**バイナリモードで**書き出す。これにより、
   正しい改行をOSが再変換する余地がなくなる。
3. 生成したバイト列を直接検証するテストを追加（`\r\r\n` を含まないこと、
   裸の `\r`/`\n` を含まないこと、`email` モジュールで読み返せること）。
   プラットフォームに依存しない形でこのクラスの不具合を開発環境でも検知できる。

**教訓**：メール／MIME形式のように**改行そのものが仕様の一部**であるデータを扱う際は、
文字列として組み立てた改行をテキストモードで書き込んではいけない。バイナリモードで
書くか、標準ライブラリに改行の管理ごと任せる。
